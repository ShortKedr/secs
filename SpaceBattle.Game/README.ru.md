# Клиент Space Battle

[Отчёт о бенчмарках](../docs/space-battle/REPORT.ru.md) |
[Обзор репозитория](../README.ru.md) |
[Происхождение ассетов](Assets/PROVENANCE.ru.md)

Интерактивный клиент Silk.NET/OpenGL 3.3 для `Battle<SecsStore>`. По умолчанию
запускаются 96 кораблей сопровождения на команду и авианосцы (всего 198),
всеми управляет AI. Для стресс-конфигурации с 4096 кораблями сопровождения
используйте `--ships 2048`.

Управление: Space ставит на паузу, +/- меняет скорость симуляции, R перезапускает
сражение с заданным seed, Home вписывает арену в экран, WASD/стрелки перемещают
камеру, перетаскивание средней/правой кнопкой также перемещает камеру, колесо
масштабирует относительно курсора, левая кнопка выбирает корабль. Верхние элементы
управления HUD кликабельны.

`Assets/ships-atlas.png` необязателен при разработке и копируется при сборке.
Прозрачный атлас содержит четыре столбца и три строки; классы 0-10 идут по строкам,
ячейка 11 зарезервирована. `ships-atlas.json` задаёт измеренные границы альфа-канала
с четырьмя пикселями прозрачного отступа для текущего изображения 1448 x 1086
с неравномерной раскладкой. Пропорции сохраняются; значения альфа ниже 33
отбрасываются, чтобы убрать слабые остатки сгенерированного фона. Без манифеста
используются равномерные ячейки 4 x 3. Без изображения HUD отмечает процедурную
замену. Корабли из атласа окрашиваются по команде; нос спрайта должен смотреть
вверх внутри ячейки. Щиты, здоровье, температура, следы и эффекты выводятся
пакетами треугольников на GPU.

Обычный запуск собранного исполняемого файла открывает видимое окно.
Автоматические снимки используют скрытое окно OpenGL, если не передан `--visible`:

```powershell
SpaceBattle.Game.exe --capture docs/space-battle/tick-900.png --capture-tick 900 --exit-after-capture --validate-render --visible
```

Запускайте из корня репозитория; пути снимков должны оставаться внутри этого
рабочего каталога. Быстрая прокрутка тиков выполняется до рендеринга и не
учитывается в накопителе реального времени. PNG читается из настоящего framebuffer
OpenGL; соседний JSON содержит количество сущностей и статистику непустых пикселей.
Метаданные снимка также сохраняют контрольную сумму состояния сражения как
16-значную шестнадцатеричную строку и SHA-256 загруженных сборок Core, Game
и адаптера SECS для отслеживания происхождения. Повторите для тиков 0, 900 и 3600.
`--ships-per-team`, `--seed`, `--width` и `--height` настраивают запуск.
`--zoom` задаёт начальный масштаб выполнения/снимка (конечные значения от 0.25
до 24, по умолчанию 1); Home/Fit по-прежнему вписывает арену в экран.
Для более плотного снимка боя используйте
`--ships-per-team 256 --zoom 2 --width 1600 --height 1000`.
Процесс завершается после снимка только по запросу. P99 относится к последним
600 тикам симуляции и не является измерением бенчмарка.
`--validate-controls` проверяет логику команд выполнения перед быстрой прокруткой:
паузу/возобновление, скорость, перемещение камеры, масштабирование относительно
курсора, вписывание, выбор и перезапуск. Это не отправляет события клавиатуры/мыши
ОС и не заменяет ручную smoke-проверку ввода.
Снаряды и обломки нейтральны к командам (`RenderEntity.Team = -1`). Цвет снарядов
обозначает только вид оружия, а не принадлежность. HUD показывает общее число
живых снарядов и накопленное число выстрелов; строки команд показывают живые
корабли, температуру и щиты. Из этого не следует наличие счётчика снарядов по
командам или иммунитета к дружественному огню.

## Профилирование Клиента

После сборки запускайте из корня репозитория:

```powershell
SpaceBattle.Game/bin/Release/net8.0/SpaceBattle.Game.exe --profile-frames 3600 --profile-warmup 120 --capture-tick 900 --ships-per-team 96 --profile-output docs/space-battle/frontend.json --profile-csv docs/space-battle/frontend.csv --hidden
```

Это **детерминированное фиксированное воспроизведение без ограничения частоты**,
а не утверждение об игровом FPS в реальном времени. VSync и оба ограничения
частоты Silk отключены. Каждый отрисованный кадр выполняет ровно один Step,
затем один Battle.Capture. Быстрая прокрутка использует `--capture-tick` без
обязательного `--capture`. Первые 120 кадров по умолчанию служат прогревом;
только следующие запрошенные кадры дают измерения. Процесс закрывается сам
после сбора последнего временного интервала и записи отчёта. Профилирование
и снимок PNG взаимоисключающие. После профилирования отдельно снимите бой.

`--hidden` скрывает окно в любом режиме. Интерактивный Update и управление
вне профилирования не меняются. В режиме профилирования ввод не может менять
воспроизведение или камеру; Escape прерывает запуск. `--validate-controls` может
проверить логику команд до начала воспроизведения, вне измерений. Количество
кадров и кадров прогрева ограничено миллионом; измеряемое число должно быть
положительным. `--profile-csv PATH` необязателен. Все пути вывода должны оставаться
внутри текущего каталога проекта.

CPU-фазы являются измерениями прошедшего времени хоста через Stopwatch, а не
аппаратными счётчиками тактов CPU. SimulationCPU охватывает Step и его скользящую
очередь HUD; SnapshotCaptureCPU охватывает только Battle.Capture.
RenderSubmissionCPU охватывает генерацию сцены/HUD, запросы телеметрии,
обновление заголовка и отправку GL clear/upload/draw. Он исключает симуляцию,
снимок состояния и обслуживание GPU-запросов. TotalCPUFrame охватывает время
от входа в callback Render до обслуживания запросов/ошибок после рисования,
исключая сохранение измерений и автоматическую смену буферов после callback.
Он включает асинхронную проверку запросов. Фазы могут включать задержки драйвера;
это не GPU-тайминги.

WallFrameInterval идёт от входа в callback Render до следующего входа. Он включает
автоматический present Silk, обработку событий и служебные операции. Последний
интервал собирается в дополнительном callback **без дополнительного Step или
рисования**. Его FPS и доля превышений 16.67 ms описывают только пропускную
способность фиксированного воспроизведения по реальному времени. Точное CPU-время
present и ожидание VSync/present остаются JSON null и пустыми в CSV: код никогда
не вычитает GPU-время из CPU-времени для оценки present.

GPU-тайминг использует GL_TIME_ELAPSED от момента перед Clear до последнего
рисования HUD. Прошедшее время на GPU может включать простои во время генерации
геометрии на CPU; это не чистая загрузка GPU полезной работой. Предварительно
выделенное кольцо из 32 запросов проверяет QueryResultAvailable и читает
64-битные наносекунды только по готовности, без блокирующего чтения результата
на каждом кадре. Кадры с занятым кольцом, неподдерживаемыми таймерами или таймерами
с нулевой разрядностью получают null, а не выдуманное нулевое время.
Поддерживаемые измерения с настоящим нулём остаются различимыми как ZeroSamples.
Все нулевые результаты или отсутствие положительных результатов на поддерживаемом
таймере приводят к ошибке проверки, а не объявляются успехом.

Всё хранилище измерений и владение запросами выделяются до измерения кадров.
JSON, CSV, процентили и хеши сборок формируются только после измерений.
Единственный GL.Finish завершает ожидающие запросы в конце после последнего
измеренного временного интервала; это ожидание исключено из всех таймингов отчёта.
Запросы удаляются до освобождения контекста GL. JSON сохраняет для каждой фазы
min/mean/p50/p95/p99/max, процентили методом ближайшего ранга, пропускную способность
по реальному времени, превышения временного бюджета CPU/реального времени,
количество GPU-измерений и null, ошибки GL, драйвер/поставщика/версию, полную
конфигурацию сражения, SHA-256 сборок и конечное контрольное состояние сражения.
Необязательный CSV содержит по одной строке на измеренный кадр со всеми
временными столбцами, превышениями бюджета и количеством сущностей.
