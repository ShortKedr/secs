## Среда Выполнения и Сценарий

Это настоящий хост .NET 8 Blazor WebAssembly для неизменённой симуляции
[SpaceBattle.Core](../SpaceBattle.Core), [SpaceBattle.SECS](../SpaceBattle.SECS)
и [SECS](../SECS) с Aether.Physics2D. Симуляция на C# выполняется в браузере;
production использует AOT-компиляцию в WebAssembly. JavaScript Canvas служит тонким
рендерером, а не переписанной на JavaScript версией боя. Прямые JS exports открывают
переиспользуемый буфер рендера в памяти WASM, без JSON-снимков и полного checksum
каждый кадр. Контрольные checksum для отладки/тестов считаются только по явному запросу.
Исходники Web-хоста и рендерера находятся в этом каталоге.

Три существующих churn-профиля: low=0.5, nominal=1 и high=2,
96 начальных эскортов и 3 авианосца на команду. Общий Core сохраняет
прицеливание с упреждением, детерминированный разброс и нейтральный к командам
урон снарядов и обломков, включая попадания по своим и в себя. Подробности
прежних правил описаны в [измеренных системах симуляции](../docs/space-battle/SYSTEMS.ru.md).
Текущие исходники используют [тактический AI `tactical-lock-v2`](../docs/space-battle/TACTICS.ru.md):
удержание цели по стоимости убийства, группы фокуса из 2-4 кораблей и прикрытие раненых.
Отчёт о бенчмарках остаётся снимком `predictive-neutral-v1`, а не замером нового AI.
Изменение локальных исходников не публикует обновление в живое демо.

## Публикация и Локальный Запуск

Из корня репозитория используйте .NET SDK 8.0.425 (или более новый патч 8.0.4xx,
выбираемый через [global.json](global.json)) и
[скрипт публикации](../tools/build-space-battle-web.ps1), выполняющий `dotnet publish`.
Для AOT закреплённому SDK нужен workload `wasm-tools`. CI устанавливает его в
одноразовый runner. Локальная установка workload за пределами репозитория остаётся
подготовкой среды самим пользователем: скрипт не устанавливает его автоматически.
`-Interpreter` предназначен только для явной локальной отладки, не для Pages.
По умолчанию `-OutputDirectory` равен `Benchmarks.Local/tmp/web-publish`,
а `-BasePath` равен `/secs/`: это путь публикации на GitHub Pages.

```powershell
./tools/build-space-battle-web.ps1
```

Для локального статического сервера публикуйте с `-BasePath /`, чтобы ресурсы
загружались от корня сервера. При установленном Python запустите сервер
в опубликованном каталоге `wwwroot`:

```powershell
./tools/build-space-battle-web.ps1 -OutputDirectory Benchmarks.Local/tmp/web-publish -BasePath /
Set-Location Benchmarks.Local/tmp/web-publish/wwwroot
python -m http.server 8000
```

Откройте [локальное демо](http://localhost:8000/) или
[его русский интерфейс](http://localhost:8000/?lang=ru). Для Pages повторите
публикацию с базовым путём `/secs/` по умолчанию; это не корневой путь локального сервера.

## GitHub Pages

[Workflow GitHub Actions](../.github/workflows/space-battle-pages.yml)
собирает и развёртывает статическое демо по
[целевому адресу Pages `/secs/`](https://shortkedr.github.io/secs/).
Демо содержит обратные ссылки на двуязычный отчёт о бенчмарках. Русский адрес демо:
[`?lang=ru`](https://shortkedr.github.io/secs/?lang=ru).
Наличие целевой ссылки само по себе не подтверждает завершение развёртывания.

Перед деплоем Actions выполняет реальные проверки в Chromium и сохраняет
desktop/mobile-скриншоты в артефакте `space-battle-browser-checks`. Проверяются
все профили, повторяемость сброса внутри браузера, счётчики боя, камера/выделение,
touch, адаптивная раскладка и восстановление после ошибки. Локальный запуск:

```powershell
./tools/build-space-battle-web.ps1
$env:PLAYWRIGHT_BROWSERS_PATH = "$PWD/Benchmarks.Local/tmp/playwright-browsers"
npm ci --prefix tools/web --cache Benchmarks.Local/tmp/npm-cache
node tools/web/node_modules/playwright/cli.js install chromium
node tools/web/check-web.mjs --base /secs/
```

В опубликованном сайте есть [состав лицензионной поставки](wwwroot/licenses/NOTICE.txt)
и оригинальные сторонние уведомления в `wwwroot/licenses/`.

## Метрики и Воспроизведение

Кнопка графика внизу открывает текущую статистику (EN/RU); краткая сводка постоянно
показывает общее число ECS-сущностей, FPS рендера, реальные тики/с и среднее время Step.
Живые сущности включают корабли в доке и за экраном, а не только видимые спрайты.
В панели отдельно показаны корабли/док, снаряды, обломки и частицы, физические тела
и коллайдеры, счётчики боя, native-память ECS/буферов доступа, управляемая куча,
архетипы/чанки и накопительные сборки GC среды. Куча не равна всей памяти
браузера/WASM/процесса; native-данные и буферы доступа показаны отдельно.

Среднее время тика, nearest-rank p95/p99, максимум и средние по стадиям используют
последние 600 выполненных тиков (до 10 секунд симуляции при 60 Гц), включая прогрев.
Обновление выполняется не чаще чем раз в 250 мс; пауза сохраняет историю, сброс
очищает её. Последовательные тики являются диагностическими отсчётами, а не
независимыми прогонами бенчмарка. Сбор выполняется вне Core Step и не меняет его
измеряемую область. Метрики передаются в бинарном заголовке, без покадрового JSON.

Реальные тики/с считают только обычные RAF-обновления за окно реального времени;
ускоренный `advanceTime` не увеличивает этот показатель. Пауза и скрытая вкладка
показывают ноль тиков/с. FPS характеризует кадры, не пропускную способность тиков.
Canvas CPU показывает сглаженное CPU-время рисования, не GPU и не весь кадр;
экспорт рендера CPU показывает последний Core capture и подготовку бинарного буфера,
включая периодическое обновление метрик. Бюджет тика равен `1000 / (60 * speed)` мс,
занятая доля равна среднему Core Step, делённому на этот бюджет. Рендер/экспорт в
него не входят; достижение заданной скорости не гарантируется. Очередь/отброшенные
тики показывают ограничение браузерного catch-up: отброшенное время не означает
пропуск игровых состояний или выполненный тик.

Демо выполняет только SECS; это не полное сравнение пяти фреймворков.
Браузерные тайминги характеризуют текущий браузер, среду WebAssembly,
устройство и условия выполнения. Рендеринг, interop, прогрев и планирование
вкладок могут влиять на работу; браузерные показатели не взаимозаменяемы
с измеренными настольными headless Step или отдельным профилем OpenGL-фронтенда.
Равенство checksum между платформами и гарантированный realtime FPS не обещаются.

[Браузерный профайлер](../tools/web/profile-web.mjs) отдельно измеряет Core Step,
подготовку буфера рендера, полный кадр фронтенда и realtime-пропускную способность
в тиках. При запущенном локальном сервере из раздела выше:

```powershell
node tools/web/profile-web.mjs --url http://localhost:8000/ --warmup-ticks 600 --output Benchmarks.Local/tmp/web-performance.json
```

Используется nominal, сид 7331, viewport Chromium 1440x900. Меняйте `--warmup-ticks`,
чтобы исследовать другие фазы боя. Замер полного кадра принудительно обновляет HUD
каждый тик; обычный цикл делает это реже. Сравнивайте на одном устройстве, в одном
браузере и одной фазе боя, не выполняя другие браузерные проверки одновременно.

Измеренное сравнение и его ограничения приведены в
[отчёте](../docs/space-battle/REPORT.ru.md). Для воспроизведения настольной кампании
следуйте [методике бенчмарков](../docs/space-battle/README.ru.md) и
[перечню реализаций и сборок](../Benchmarks.Local/README.ru.md).
Публикация или запуск демо не пересоздаёт и не заменяет эти измерения.
