# План тестов детерминизма SECS

Для текущего CPU SECS можно автоматизировать повторные прогоны и сравнение результатов между Windows, Linux, macOS, x64 и ARM64 в GitHub Actions. Начать следует с целочисленного набора сценариев ECS, независимого эталона и общего формата состояния. Равенство произвольной игровой логики с float, а также CPU/GPU, требует дополнительных контрактов и исполнителей.

Статус на 12 октября 2026 года: план реализации. [Пример workflow](secs-determinism.example.yml) запускает существующие тесты и находится вне `.github/workflows`; он ещё не проверяет равенство трасс между машинами. Новый replay runner, эталонные трассы и comparer предстоит реализовать по этапам ниже.

## Что уже проверяется

[SECS](../SECS/SECS.csproj) и [SECS.Tests](../SECS.Tests/SECS.Tests.csproj) имеют target `net8.0`. В библиотеке нет GPU backend или параллельного scheduler. Текущий набор содержит 16 `[Fact]` и ни одного `[Theory]`:

| Файл | Тестов | Покрытие |
| --- | ---: | --- |
| [WorldTests](../SECS.Tests/WorldTests.cs) | 7 | Компоненты, destroy и версии ID, обновление query cache, обход строк и чанков, стадии систем, миграции |
| [AccessorSwapTests](../SECS.Tests/AccessorSwapTests.cs) | 3 | Accessor после миграций и swap удаления, уничтожение, lifetime factory и повторные типы |
| [DefaultWorldTests](../SECS.Tests/DefaultWorldTests.cs) | 1 | Default options и несколько чанков при capacity 256 |
| [OptimizationTests](../SECS.Tests/OptimizationTests.cs) | 5 | Churn с seed 7319, переиспользование чанков, accessors, direct и batch создание |

Зафиксированная локальная проверка 12 октября 2026 года: Release 16/16 и Debug 16/16, без пропусков; Windows x64, SDK 10.0.204, target net8.0. TRX находятся в `Benchmarks.Local/tmp/secs-determinism-plan/tests`. Это проверка существующих контрактов на одной машине. Набор ещё не сравнивает независимые процессы, разные ОС или архитектуры.

У [SpaceBattle.Headless](../SpaceBattle.Headless/Validation.cs) есть повтор двух боёв в одном процессе с финальным checksum после 1800 тиков и сравнение пяти ECS адаптеров через каждые 300 тиков до 3000. Это полезный интеграционный слой. [Battle.Checksum](../SpaceBattle.Core/BattleInspection.cs) хеширует выбранные поля, включая биты float; он не является полным снимком ECS, физического solver или всего состояния, влияющего на продолжение симуляции. Headless отчёт также содержит время, память, дату и имя машины, поэтому целые JSON файлы нельзя сравнивать побайтно.

## Предлагаемый контракт

| Уровень | Что должно совпадать | Условия |
| --- | --- | --- |
| D1 Повтор одного журнала | Результаты API, ID и версии, состав компонентов, значения, трасса обхода и вызовов систем | Одинаковые последовательные операции, регистрации типов и систем, options и среда |
| D2 Переносимость ECS | Канонические состояния и наблюдаемые результаты D1 между выбранными ОС и CPU | Фиксированные входы, схема сериализации и определённая целочисленная арифметика |
| D3 Независимость от хранения | Логическое состояние при разных capacities, подготовке queries и регистрации типов | Только системы, явно независимые от порядка обхода; внутренние ID типов и адреса исключены |
| D4 Игровой replay | Состояние игрового сценария после каждого тика | Свой контракт чисел, RNG, событий, физики и всех скрытых состояний |
| D5 CPU/GPU | D2 или D4 для одного исходника системы и разных исполнителей | GPU backend, правила конфликтов записи, структурных команд и арифметики |

Для первого обязательного CI выбрать D1 и D2 на целочисленных компонентах, затем D3 для независимого обновления каждой сущности. D4 начать как отдельную диагностику SpaceBattle; D5 подключить после появления исполняемого GPU backend. Успешная конечная матрица подтверждает конкретный workload и набор сред, а не доказывает детерминизм всех C# систем на любом оборудовании.

Решения до реализации:

1. Зафиксировать последовательное исполнение и запретить структурные изменения внутри активного обхода в контракте тестовых сценариев. Сейчас [Query](../SECS/Query.cs) читает живые списки и передаёт `ref`; отложенной очереди изменений или snapshot гарантий нет. Операции добавления и удаления выполнять между обходами. Для публичной поддержки иной семантики сначала понадобятся отдельное решение и тесты API.
2. Для D1 фиксировать capacity и порядок регистрации. [World](../SECS/World.cs) хранит архетипы в порядке создания, системы в порядке регистрации, свободные entity ID в LIFO стеке. [Archetype](../SECS/Archetype.cs) использует swap удаление внутри чанка. Query посещает архетипы, чанки и строки, а не сортирует entity ID. Порядок зависит от истории операций; его независимость от истории не обещать.
3. Для D3 сравнивать набор сущностей и поля отдельно от трассы посещений. Например, `value += velocity` независимо для каждой сущности подходит, а изменение общего аккумулятора с зависимостью от предыдущего результата требует явно определённого порядка. При перестановке создания сущностей сопоставлять их по стабильному логическому ключу сценария, а не ожидать тех же entity ID.
4. Фиксировать семантику переполнения арифметики сценария (`checked` или `unchecked`), разрядности и деления. Переполнение generation у Entity и операции с невалидным или чужим handle оставить отдельными вопросами API. В частности, диагностика части invalid handles в World зависит от `DEBUG`; для Debug/Release сравнивать допустимые операции.
5. Не включать многопоточность одного World, изменение регистрации систем во время Run и повторный вход в Run в гарантию D1. Сначала определить их разрешённость; нынешние живые списки не дают snapshot поведения. Негативные тесты добавлять после выбора ожидаемого поведения, чтобы не закрепить случайный результат.

## Каноническое состояние и эталон

Сделать небольшой `SECS.Determinism` console проект, зависящий только от SECS, и общие сценарии для xUnit. Он должен запускаться без окна, OpenGL, SpaceBattle, vendor адаптеров и WASM toolchain. Команды workload хранить как версионированные fixtures; создание fixtures отделить от их исполнения. Seed сам по себе не описывает полный вход.

Нужны два представления результата:

- **Логический снимок:** все живые сущности, включая сущности без компонентов; ID и version для того же журнала, стабильные schema ID типов, наличие компонентов и каждое определённое поле. Сортировка по identity и schema ID; длины секций, фиксированные разрядности и little endian. Связи между сущностями сериализовать как identity. Для перестановочных сценариев использовать логические ключи. Harness хранит журнал выданных handles, поскольку публичного универсального serializer и перечисления всех полей в SECS нет.
- **Трасса наблюдаемого поведения:** результаты команд, выдача новых handles, посещения query, этапы и вызовы систем. Её сравнивать при фиксированном порядке D1 отдельно от отсортированного состояния. Для проверки скрытой истории хранения продолжать одинаковым суффиксом команд, включающим создание после destroy и миграций.

Нельзя хешировать указатели, accessor адреса, `Entity.GetHashCode()`, внутренние numeric type ID, весь chunk или `sizeof(T)` сырые байты. [ComponentTypeRegistry](../SECS/ComponentTypeRegistry.cs) присваивает world type ID по первому обращению; unmanaged структуры могут содержать padding, а память чанков выделяется без общей инициализации. Канонический writer должен писать определённые поля живых объектов. Для float хранения отдельно выбрать точные IEEE биты, включая знак нуля и payload NaN; нормализация допустима только как явно другой контракт. Не вводить epsilon в строгую проверку равенства.

Канонические байты хешировать SHA-256. Хеш после каждой операции или тика нужен для быстрого поиска расхождения, а небольшие сценарии сравнивать ещё и полностью. При ошибке выдавать первую операцию или тик, entity, компонент, поле, ожидаемое и фактическое значение, входной fixture и оба снимка. Проверить сам writer и comparer: перестановка допустимого порядка сериализации не меняет снимок; изменение одного поля, membership, version или результата команды обязательно обнаруживается.

Эталон состоит из небольших вручную проверяемых fixtures и простой managed модели на словарях и наборах, без архетипов, unmanaged storage и query cache. Модель проверяет состав и значения компонентов, результаты команд и порядок стадий систем. Порядок посещения query проверять отдельно: вручную заданным golden для маленьких fixtures и сравнением повторов, процессов и платформ для остальных. Managed модель не должна копировать внутреннюю организацию чанков ради предсказания этого порядка. Два повтора SECS обнаруживают нестабильность, но могут одинаково воспроизводить ошибку; логическое состояние обоих должно совпадать с независимой моделью. При намеренной смене контракта ожидаемые результаты изменять отдельным проверяемым изменением; CI не должен автоматически перезаписывать golden файлы.

Для случайных сценариев использовать сохранённый журнал операций либо версионированный собственный генератор с известными векторами. Текущий `System.Random(7319)` удобен для локального churn, но Microsoft не гарантирует одинаковую последовательность между major версиями .NET. [Контракт System.Random](https://learn.microsoft.com/en-us/dotnet/api/system.random?view=net-10.0).

| Приоритет | Сценарий | Проверка |
| --- | --- | --- |
| P0 | Один fixture в двух свежих World, затем два запуска нового процесса | Полные результаты команд и состояния на каждом шаге совпадают с эталоном |
| P0 | Create, Add, Remove, Destroy, повторное создание | Те же ID и версии для того же журнала, данные survivors и membership; пустые сущности тоже учтены |

| P0 | Системы и стадии | PreUpdate, Update, PostUpdate; несколько систем в стадии, повтор RunAll, влияние порядка и данные после каждой системы |

| P1 | Независимые системы при разных capacities | Integer Transform и Motion: одно и то же покомпонентное обновление через ForEach и Chunks, равенство D3 |
| P1 | Тип с padding и повторное использование памяти | `byte` и `int` поля после create/migrate/destroy; равенство определённых полей без чтения padding |
| P1 | Переносимость чисел и сериализации | Min/max целых, переполнение по выбранной политике, отрицательное деление, byte order; float copy без арифметики с ±0, subnormal, Infinity, NaN |
| P2 | Длительный churn и рост | Несколько fixtures, расширение registry/query cache, исчерпание и переиспользование чанков, состояние и observable continuation |

Для PR предложенный объём: 4 fixtures с seeds 1, 27, 7331, 4294967295, до 2000 операций каждый, два отдельных процесса; границы и options проверять короткими параметризованными тестами. Для nightly: 16 fixtures до 100000 операций каждый и дополнительные варианты JIT. Это исходный бюджет workload; время и объём artifacts измерить после реализации runner. Если генератор поддерживает seed 0, отдельно определить его поведение и вектор.

## GitHub Actions

CPU тестам достаточно SDK, NuGet restore и обычных runners. Минимальную матрицу строить так:

| Label | ОС | CPU | Назначение |
| --- | --- | --- | --- |
| `ubuntu-24.04` | Linux | x64 | Основная матрица и reference job |
| `windows-2022` | Windows | x64 | Основная матрица |
| `ubuntu-24.04-arm` | Linux | ARM64 | Архитектурная переносимость |
| `macos-15` | macOS | ARM64 | Другая ОС на ARM64 |
| `macos-15-intel` | macOS | x64 | Расширенная nightly матрица |

Эти labels перечислены для public и private repositories в [справочнике GitHub runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Label ОС не фиксирует точную модель CPU или неизменяемый образ. Runner обязан записывать фактические OS, process architecture, SDK, runtime, JIT options, commit, fixture digest и schema version. Архитектуру процесса проверять явно: x64 процесс через эмуляцию не является ARM64 проверкой.

Проект target `net8.0` запускается на .NET 8 даже при сборке новым SDK. Для отдельной проверки .NET 10 нужно обеспечить запуск на этом runtime, например отдельным target тестового host, и записать фактическую версию; установка второго SDK сама по себе runtime матрицу не создаёт. На этапе D2 фиксировать точный SDK и разрешённый runtime patch. `setup-dotnet` без `global.json` не исключает выбор более нового предустановленного SDK; пример фиксирует выбор установленного SDK временным global.json. [Документация setup-dotnet](https://github.com/actions/setup-dotnet).

На 12 октября 2026 года .NET 8 поддерживается до 10 ноября 2026 года, а .NET 10 до 14 ноября 2028 года. Начать с текущего net8, но сразу запланировать проверку совместимости тестового host и библиотеки с .NET 10; переход target является отдельным изменением. [Политика поддержки .NET](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core).

Последовательность CI после реализации replay:

1. Каждая комбинация ОС и конфигурации делает restore и build конкретных SECS проектов, запускает xUnit выбранной конфигурации, затем один и тот же replay в двух отдельных процессах этой конфигурации. Сравниваются также Debug и Release для допустимых целочисленных сценариев. `fail-fast: false` сохраняет диагностику остальных сред.
2. Job проверяет оба результата локально и по managed эталону, затем сохраняет manifest, fixtures, per-step hashes, канонические снимки и TRX. Artifact name содержит label, configuration и вариант запуска; выгрузка происходит с `if: always()`.
3. Отдельная `compare` job с `needs` всех producer jobs и `if: always()` скачивает результаты и проверяет ожидаемый полный inventory. Отсутствующий, пустой, лишний, несовместимый по schema/input/runtime результат или ошибка producer должны делать gate красным. Сначала сопоставить metadata, затем сравнить per-step hashes и полные снимки с golden и между средами.
4. PR gate сравнивает целочисленные D1/D2 результаты. Для D3 сравнивается только логическое состояние независимых сценариев. Отдельный диагностический job SpaceBattle не влияет на утверждение о переносимости ECS.
5. Обязательный status check имеет стабильное имя, например `SECS determinism`, и зелёный только при успехе всей необходимой матрицы. Если включён merge queue, нужен также `merge_group`. Не скрывать расхождения через `continue-on-error` или повторные запуски до первого успеха.

[upload-artifact](https://github.com/actions/upload-artifact) и [download-artifact](https://github.com/actions/download-artifact) передают данные между jobs. Сравнивать симуляционные поля, а не архивы или целые manifest: timestamps, timings, OS и CPU ожидаемо различаются.

Triggers: `pull_request`, `push` на main и `workflow_dispatch`; для долгих сценариев отдельный `schedule`. Обязательный PR workflow лучше запускать без paths фильтра: GitHub предупреждает, что пропущенный по paths workflow оставляет required check в Pending. [Поведение skipped workflows](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs).

Достаточны `permissions: contents: read`, checkout без сохранения credentials и стандартный artifact transport. Secrets, публикация Pages, GPU, установка workload, сборка solution целиком и benchmark запуск для CPU набора не нужны. Изменения на GitHub для будущего включения: разрешить Actions и используемые actions, добавить workflow, при необходимости назначить gate обязательным в правилах ветки. Это настройки владельца репозитория; пример не активирует их.

Кэш NuGet необязателен. До `setup-dotnet cache: true` и `restore --locked-mode` нужно создать и проверить packages.lock.json для тестового dependency graph; сейчас test проекта их нет. Для первого запуска пример использует обычный restore без cache. Build outputs между архитектурами не переиспользовать.

По текущей [политике оплаты GitHub Actions](https://docs.github.com/en/billing/concepts/product-billing/github-actions), standard hosted compute бесплатен для public repositories; private используют квоты плана, artifacts имеют ограничения хранения, larger runners оплачиваются отдельно. Начальная матрица из 4 сред и 2 конфигураций даёт 8 jobs. Например, при предположении 3 минут на job это 24 минуты суммарного исполнения без учёта тарифных правил; это оценка, а не измеренный CI результат. Для artifacts начать с retention 7 дней, хранить полные снимки маленьких fixtures и снимки первого расхождения для stress.

## Игровая математика и GPU

SECS хранит unmanaged компоненты и вызывает пользовательский processor; библиотека не определяет арифметику этих систем. Поэтому portable float copy и portable simulation с тригонометрией являются разными тестами. Даже документация [Math.Sin](https://learn.microsoft.com/en-us/dotnet/api/system.math.sin?view=net-8.0) допускает различия точного результата между ОС и архитектурами. Для строгого игрового контракта выбрать integer/fixed point с определёнными округлением и intermediate width либо тщательно ограниченный и проверяемый float профиль. Float системы сначала запускать диагностически и сохранять расхождения.

Перед полноценным SpaceBattle D4 дополнить снимок всеми состояниями, определяющими следующий тик: очереди spawn/destroy, события, RNG, timers и состояние физики. Существующие validation и checksum полезны как smoke tests; renderer и screenshot не проверяют детерминизм симуляции.

GitHub предлагает GPU larger runners с NVIDIA Tesla T4 на Ubuntu и Windows. Они доступны организациям с GitHub Team или Enterprise Cloud и оплачиваются; это не покрывает AMD, Intel, Apple, Adreno или Mali. [Спецификации](https://docs.github.com/en/actions/reference/runners/larger-runners), [доступность larger runners](https://docs.github.com/en/actions/concepts/runners/larger-runners).

Первый D5 workload: один исходник независимой целочисленной Transform плюс Motion системы, CPU reference и один GPU backend, те же входы и состояние после каждого тика. Потребуются компилятор или перевод поддерживаемых систем, buffers и readback, barrier и write semantics, детерминированные events и structural commits. В GPU job принудительно выбирать GPU backend и записывать фактический device, API и driver; незаметный CPU fallback не должен считаться GPU успехом.

Для проверки других производителей и мобильных API понадобятся выделенные self-hosted машины или парк устройств. Android и iOS не входят в указанную матрицу hosted desktop runners. GPU и device jobs следует подключать отдельным этапом на проверенном коде; отсутствие устройства означает непроверенную комбинацию. Новую backend матрицу нельзя заменить несколькими CPU архитектурами.

## Этапы реализации

| Этап | Локальные изменения | Критерий готовности |
| --- | --- | --- |
| 1 | Параметризованные `SECS.Tests/DeterminismTests.cs`, schema, managed oracle и маленькие fixtures | D1 тесты проходят в Debug и Release; writer/comparer обнаруживает намеренное повреждение |
| 2 | `SECS.Determinism/` console host, общий workload, `tools/determinism/compare.py`, эталонные traces | Два независимых процесса равны эталону; первый несовпавший шаг даёт полезный diff |
| 3 | `.github/workflows/secs-determinism.yml`, matrix и aggregate gate | Все необходимые artifacts получены; D2 результаты равны; потеря artifact или mutation делает gate красным |
| 4 | Nightly stress, D3 варианты хранения, отдельные SpaceBattle проверки | Длинные workloads воспроизводимы; область подтверждённого контракта записана явно |
| 5 | Общий контракт CPU/GPU и один backend, затем устройство за устройством | Исполнители совпадают на каждом тике; fallback и непроверенные устройства отмечены явно |

Начать с этапов 1–3. [Workflow пример](secs-determinism.example.yml) уже описывает multi-platform запуск существующих 16 тестов, но его aggregate check называется `SECS baseline`: переименовать в determinism gate следует после добавления replay и обязательного сравнения artifacts.
