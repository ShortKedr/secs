# Обложка текущего геймплея

[Проект](../../README.ru.md) | [Отчёт](REPORT.ru.md) | [Методика бенчмарков](README.ru.md)

`cover.png` показывает текущий геймплей нативного OpenGL-клиента. Это не
зафиксированный измеренный прогон, не бенчмарк и не доказательство
производительности в реальном времени. Исторические `action.png` и
`action.png.json`, их перечень хешей, записи parity и все файлы измерений
остаются неизменными.

## Конфигурация и локальный захват

Источник параметров: [cover-settings.json](cover-settings.json), который читает
[cover.py](../../tools/space-battle/cover.py). Для изменения сцены меняйте эту конфигурацию;
не поддерживайте второй набор констант захвата в документации или командах
workflow. Планируемый пресет: seed 7331, 96 кораблей на команду, tick 180,
1600 x 1000 пикселей и zoom 2. Источник истины: файл настроек, а не это описание.

Локальное воспроизведение использует Python, .NET 8 и настоящий нативный
рендерер под Linux Xvfb/Mesa. Соберите клиент и используйте helper с JSON
настроек; это только захват, без серии бенчмарков или анализа отчёта. Кадр
выбирается по тику симуляции, а не прошедшему реальному времени: медленный
рендерер всё равно должен достичь заданного тика перед сохранением.
Фиксированные настройки делают сцену воспроизводимой; побайтовое совпадение
PNG между графическими драйверами не обещается.

Из корня репозитория, после сборки клиента в ту же изолированную папку
артефактов, что и в workflow:

```bash
python -m pip install -r tools/space-battle/cover-requirements.txt
xvfb-run -a -s "-screen 0 1920x1200x24 +extension GLX +render -noreset" \
  python tools/space-battle/cover.py capture \
  --assembly Benchmarks.Local/tmp/cover-build/bin/SpaceBattle.Game/release/SpaceBattle.Game.dll \
  --source-commit "$(git rev-parse HEAD)"
python tools/space-battle/cover.py validate \
  --directory Benchmarks.Local/tmp/space-battle-cover --allow-dirty
```

На Windows уберите префикс `xvfb-run` и передайте хеш локального HEAD строкой
в `--source-commit`. Незакоммиченные локальные кадры помечаются `SourceDirty`;
`--allow-dirty` используется только при локальной проверке, никогда в Actions.
Захват пишет в `Benchmarks.Local/tmp/space-battle-cover`, а не в документы.

## Проверка и публикация

Контракт [workflow](../../.github/workflows/space-battle-cover.yml): push в `main` или
`workflow_dispatch` на `main`. Workflow собирает и захватывает фактический
commit исходников настоящим OpenGL-клиентом под Linux Xvfb/Mesa, а не
имитацией рендера или браузерным демо.

PNG и соседний manifest подготавливаются во временной области и проверяются
как пара до публикации. Проверяются заданные тик, размеры и seed, непустой
рендер и счётчики отрисовки; записанное происхождение исходников сравнивается
с фактическим commit, из которого сделан захват. [cover.png.json](cover.png.json) содержит
commit исходников, SHA256 собранных бинарников, seed, checksum симуляции и счётчики отрисовки;
они описывают эту обложку, а не исторический бенчмарк. Невалидная или
несогласованная пара не должна заменять опубликованную обложку.

Seed записывается из точных аргументов запуска клиента: в сыром нативном
sidecar этого поля нет. Проверка активности требует хотя бы 24 отрисованных
корабля, живых кораблей обеих команд и хотя бы одного активного снаряда.
Это защита от пустого или завершённого боя, а не проверка производительности.
Если изменение геймплея нарушило эти условия, осознанно скорректируйте фиксированный
тик. Сырые нативные тайминги остаются в артефакте; manifest обложки их исключает
и не является отчётом бенчмарка.

Единственные публикуемые файлы: `docs/space-battle/cover.png` и
`docs/space-battle/cover.png.json`. Commit бота использует `GITHUB_TOKEN`,
никогда PAT. Commit с этим токеном не запускает другие workflows, поэтому
обновление обложки не вызывает рекурсивный запуск этого workflow. Защита
ветки или политика репозитория для `contents: write` могут заблокировать
публикацию; при её отказе захваченная пара остаётся доступной как артефакт
workflow.

Пересекающиеся запуски уступают последнему push. Перед публикацией job
проверяет, что `main` всё ещё указывает на просимулированный commit; устаревший
результат пропускается. Последний push допускает только fast-forward и не может
перезаписать конкурентное изменение исходников.
GitHub описывает [защиту GITHUB_TOKEN от рекурсии](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

Это описание планируемого контракта автоматизации, а не утверждение об
успешной проверке живого запуска GitHub или публикации ботом.
