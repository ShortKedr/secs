# Оптимизация Пространства Space Battle

[Отчёт о симуляции](REPORT.ru.md) | [Предыдущее исследование](PERFORMANCE_INVESTIGATION.ru.md)

Локальное исследование текущей симуляции с отдельными пушками, 2026-10-12. Здесь сравнивается SECS до/после изменения алгоритмов, а не составляется новый рейтинг пяти ECS. Зафиксированные результаты бенчмарков и удалённое состояние не изменены.

## Где Терялось Время

- Каждый снаряд и осколок запускал до пяти raycast и пяти проверок перекрытия стартовой точки, в том числе в пустом пространстве. Broadphase-дерево у Aether уже было, но симуляция многократно обходила его для одной траектории.
- Движущиеся сущности запрашивались, собирались и сортировались в начале и конце тика, затем ещё раз для кадра. Большинство изменений состава уже было известно из запросов создания/удаления.
- Поиск угроз многократно сканировал все корабли, в том числе из вложенных вызовов при выборе укрытия. Группы, укрытия и пушки перебирали корабли за пределами нужных им расстояний.
- Каждый запрос докования заново считал занятые места, каждая постройка заново считала подчинённые корабли. Для каждого погибшего корпуса сканировался весь список пушек, а удаления многократно сдвигали элементы списка.

## Изменения И Сложность

`S` = корабли, `G` = группы, `T` = пушки, `E` = сущности, `K` = ближайшие кандидаты, `Q` = запросы докования, `B` = запросы постройки, `D` = погибшие корпуса, `A` = их прикреплённые пушки.

| Участок | Было | Стало |
| --- | --- | --- |
| Пустая траектория попадания | До 5 лучей + 5 проверок точки | Один консервативный AABB-запрос; без narrow phase при пустом результате |
| Угрозы за один снимок | Повторные полные `O(S)` проходы, иногда вложенные | Построение обратного индекса за `O(S)`, каждое входящее ребро проверяется не более раза при кешированном поиске угроз |
| Группы и укрытия | Полные проходы по флоту/группам | Сетки точек/лидеров; точные правила проверяются на `K` кандидатах с прежним порядком равных результатов |
| Выбор цели пушки | Полные проходы `O(T*S)` | Локальные кандидаты для каждой ищущей пушки |
| Учёт доков/построек | `O(Q*S + B*S)` | `O(S+Q)` только при запросах докования; `O(S+B)` только при запросах постройки |
| Удаление прикреплённых пушек | `O(D*T)` и повторные сдвиги | Одно построение индекса текущих владельцев при необходимости, `O(T+A)`, затем одно уплотнение списка |
| Движущиеся сущности в конце тика | ECS-запросы и сортировки `O(E log E)` | Стабильное уплотнение `O(E)`; обычные возрастающие serial не требуют сортировки |
| Захват кадра после Step | Дополнительные сбор и сортировка | Использует готовые списки; упаковка кадра остаётся `O(E)` |

Упорядочивание кандидатов требует `O(K log K)`, когда результат сетки собирается из неупорядоченных ячеек. Буферы ячеек и запросов переиспользуются. Сетка строится по неизменяемому снимку до принятия решений, а не по частично обновлённому AI. Порядок равных расстояний, удержание целей, RNG, нейтральные/friendly/self попадания и переходы lifecycle по serial сохранены.

Предфильтр попаданий охватывает фактические float-координаты концов пяти лучей и запросов их стартовых точек с запасом на округление. Отбрасывается только пустой broadphase-результат. Для кандидатов остаётся исходный narrow phase: приближённый CCD из пяти лучей не превращён в точный swept disk и не дополнен CCD движущихся целей.

`Capture(frame)` по-прежнему синхронизирует списки после прямых изменений Store. Native/web используют `Capture(frame, refreshEntities: false)` только с готовыми списками после создания симуляции или `Step`. После прямых изменений Store нужен обычный обновляющий захват. Принадлежность пушек индексируется по текущим компонентам перед пакетом уничтожений, а не считается неизменяемой.

## Измерения

Миллисекунды за тик/вызов; сокращение означает сэкономленное CPU-время, а не обещание FPS.

| Сценарий | До | После | Сокращение Времени |
| --- | ---: | ---: | ---: |
| Native, 96 сопровождающих/команда, тики 1-600 | 1.704 | 1.025 | 40% |
| WASM core, тики 1-600 | 10.173 | 6.053 | 40% |
| WASM core + бинарный экспорт, тики 1-600 | 12.875 | 6.925 | 46% |
| Только WASM экспорт + interop, тики 1-600 | 2.702 | 0.871 | 68% |
| WASM core, тики 601-1200 | 5.458 | 3.225 | 41% |
| Native стресс, 384 сопровождающих/команда, тики 1-600 | 8.952 | 5.963 | 33% |

Диапазоны средних по прогонам: native стандарт 1.695-1.712 -> 1.006-1.025 мс; WASM стандарт 10.105-10.241 -> 6.020-6.083 мс; native стресс 8.490-9.658 -> 5.926-6.021 мс. Это наблюдаемые эффекты, не формальная проверка статистической значимости. В стандартном native обработка попаданий снизилась с 0.955 до 0.442 мс, lifecycle с 0.216 до 0.038 мс. AI не ускоряется в каждом окне с небольшим населением: построение индекса тоже стоит времени.

Медианный браузерный core P95 снизился с 16.0 до 10.7 мс, но наблюдаемые максимумы оптимизированной версии остаются 17.7-18.2 мс. Рендер исключён: это не гарантия того, что каждый полный кадр укладывается в бюджет 16.67 мс.

В первых 600 тиках браузера 736,902 из 790,785 траекторий (93.2%) отбрасываются без narrow-phase лучей/проверок точек; в тиках 601-1200 это 1,045,753 из 1,054,317 (99.2%). Убрана лишняя работа, не урон: контрольные суммы и игровые счётчики до/после совпадают.

По три независимых свежих прогона для каждой сборки/сценария, отдельный прогрев на 600 тиков, seed 7331, частицы включены. Порядок версий чередуется. В таблицах медиана средних по прогонам, а не самый быстрый тик или удачный прогон. Native `Step` не включает рендер/захват. Браузерный `Advance(1)` включает бинарный экспорт кадра, но Canvas/DOM при измерении остановлены; это настоящий Mono AOT, не интерпретатор. Компиляция и замеры не перекрываются. Фоновая нагрузка и планировщик всё равно добавляют шум, особенно в стресс-сценарии.

Native: .NET 8.0.31 CoreCLR/Release; web: SDK 8.0.425, .NET 8.0.31 Mono AOT/LLVM `-O2`, Chromium headless, 1440x900. Стандартный старт: 96 сопровождающих кораблей и три авианосца на команду; стресс: 384 сопровождающих на команду. Население стресс-сценария убывает в бою, поэтому это средние за окно повтора, а не гарантия пропускной способности при неизменной численности.

Внутри каждого runtime совпадают контрольные суммы, счётчики и состав до/после. Побитовая идентичность native и WASM друг другу не утверждается; их отношение таймингов нельзя считать чистыми расходами компилятора. Исходное длительное сравнение пяти фреймворков не заменено.

## Проверки И Воспроизведение

- 30,203 дифференциальных проверки траекторий: случайные короткие/длинные/неподвижные пути, составные/круглые фигуры, движение, вращение, отключённые тела, нулевой радиус, касательные траектории, равные serial-условия и идентичные координаты попаданий.
- Готовые кешированные кадры совпадают с полным сбором ECS при боевом churn. Внешнее создание/истечение жизни снарядов видно через обычный API.
- Проверяются границы ячеек, отрицательные координаты, консервативные кандидаты, порядок групп при равных расстояниях, обратные угрозы, приоритет недавнего атакующего, докование, укрытия и сброс кеша. Прогретая сетка не выделяет новые буферы.
- Все пять адаптеров проверяют смену владельца пушек/гибель и конкуренцию за доки с одновременным отстыковыванием/уничтожением в обоих порядках serial.
- Все пять адаптеров воспроизводят исходные десять native-checkpoint за 3,000 тиков с итогом `DC7DFAFE4769F423` при 16 сопровождающих на команду и seed 27. Проверки геймплея, вооружения и ECS тоже проходят.

```powershell
dotnet build SpaceBattle.Headless/SpaceBattle.Headless.csproj -c Release --artifacts-path Benchmarks.Local/tmp/spatial-verified
dotnet Benchmarks.Local/tmp/spatial-verified/bin/SpaceBattle.Headless/release/SpaceBattle.Headless.dll --validate
dotnet Benchmarks.Local/tmp/spatial-verified/bin/SpaceBattle.Headless/release/SpaceBattle.Headless.dll --validate-ports
node --test tools/space-battle/test_summarize_spatial.mjs
```

[Браузерный профайлер](../../tools/web/profile-revisions.mjs) принимает `--sites` с двумя локальными корнями опубликованных сборок и затем закрывает localhost-серверы. [Генератор сводки](../../tools/space-battle/summarize-spatial.mjs) отказывается обобщать результаты с изменённой траекторией геймплея. Сборки/сырые временные результаты остаются в игнорируемом `Benchmarks.Local/tmp`; отдельные [данные сводки](spatial-optimization/summary.json) содержат независимые средние, диапазоны, native-стадии, счётчики и хеши бинарников.

## Что Ещё Затратно

Глобальный выбор цели по стоимости убийства по-прежнему перебирает всех врагов в тики принятия решений. Худший случай по всем актёрам остаётся `O(S^2)`. Текущие правила допускают преследование далёкой достижимой цели: произвольный радиус изменил бы поведение AI. Для дальнейшего безопасного отсечения нужна доказанная нижняя граница стоимости убийства, а не подмена выбора ближайшим врагом.

В плотной ячейке может оказаться весь флот, а настоящие перекрывающиеся физические контакты могут потребовать квадратичного числа кандидатов. Broadphase сокращает лишнюю работу, но не стоимость реально взаимодействующих пар. Сбор кораблей на границах тика сохранён для совместимости с внешними изменениями Store. Упаковка кадра, рендер и проверки ECS-доступа остаются отдельными затратами; их полное устранение здесь не заявляется.
