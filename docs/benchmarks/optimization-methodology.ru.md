Этот отчёт сравнивает исходные результаты бенчмарков SECS с результатами
оптимизированной версии для тех же сценариев нагрузки. Сравнение намеренно ограничено
SECS; наличие других фреймворков в JSON оптимизированной версии не требуется. Исторические
`Benchmarks.Local/results.json` и `stress-results.json` остаются неизменными. Для
сопоставимого сравнения до и после оптимизации график по умолчанию использует свежие
повторные замеры исходной базовой версии из `results-baseline-repeat.json` и
`stress-baseline-repeat.json`; замеры оптимизированной версии записаны в отдельные
файлы `results-optimized.json` и `stress-results-optimized.json`. Все четыре
пути можно переопределить через командную строку. Замеры выполнены
2026-10-11 с использованием .NET 8.0.31 x64, Release, одного потока и отключённой многоуровневой компиляции.

## Покрытие и представление

Базовый набор включает `Create`, `Iterate`, `Churn` и `Destroy` для 1,000 и
100,000 сущностей. Стресс-набор включает `DenseIteration`, `SparseIteration`,
`WideIteration`, `RandomLookup`, `PayloadChurn`, `Recycle10Percent` и
`MixedFrames` для 100,000 и 1,000,000 сущностей. Сравниваются только сценарии,
присутствующие в обеих версиях; сценарии без пары обозначаются на графике,
а не восстанавливаются предположениями или подстановкой значений.

Каждая панель показывает среднее время исходной и оптимизированной версий с усами
в размере одного стандартного отклонения, если есть `stddevNs`. Для базовых панелей
выбираются микросекунды или миллисекунды на операцию; время стресс-сценариев выражено
в миллисекундах на полную операцию. У каждого сценария собственная логарифмическая
шкала времени, поэтому сравнивайте парные столбцы и их численные подписи внутри
панели, а не длину столбцов между панелями. Ускорение вычисляется как
`original meanNs / optimized meanNs`: значение выше 1 означает, что оптимизированный
сценарий быстрее, ниже 1 означает, что он медленнее. Отношение описывает
эти запуски, но не является проверкой статистической значимости.

## Контекст измерений

Исходные результаты сравнения получены локальным измерительным стендом на Stopwatch,
а не BenchmarkDotNet. Он проверяет нагрузку до измерения времени, прогревает каждый
сценарий и сообщает результаты повторных выборок. Подготовка, освобождение ресурсов
и принудительная сборка мусора исключены из измеряемого интервала; сборка мусора,
вызванная операцией, включена. Стресс-стенд использует одинаковые фиксированные
входные данные нагрузки и порядки с фиксированным seed для каждого фреймворка,
но имеет собственные правила выборок и прогрева. Полные определения нагрузок
и описание стенда приведены в
[`SECS.Benchmarks/README.ru.md`](../../SECS.Benchmarks/README.ru.md).

И исходная базовая версия, и оптимизированная реализация выполняют нативную
среду выполнения SECS. Повторный замер исходной базовой версии использует
сохранённый скомпилированный `Benchmarks.Local/baseline-bin/SECS.dll`; туда копируется
только `Comparison.dll`, чтобы выполнить те же API-сценарии с этой библиотекой.
`SECS.dll` нельзя заменять сборкой из оптимизированных исходников. Метка ревизии
SECS в метаданных свежего повторного замера базовой версии исправляется через
переопределение метки ревизии переменной окружения стенда, чтобы она обозначала
сохранённую базовую версию, а не текущее рабочее дерево. Происхождение бинарного
файла следует отличать от метки в метаданных.

Исходная ревизия кода: `872e0df`. SHA-256 сохранённой исходной DLL:
`D7996FF91C3DFE4414E41E79D2E0CDE636DAE0DC706C6F8A2254F82B3C8678AC`.
На момент измерения оптимизированная среда выполнения была незакоммиченным патчем рабочего дерева.
Для каждого базового сценария сохранено 20 выборок, для каждого стресс-сценария 8 выборок.
Исходные тестовые сценарии и операции адаптера SECS не заменялись новыми API аксессоров и фабрик.

Измеренная здесь оптимизация добавляет API аксессора, но исходные тестовые сценарии
не регистрируют и не используют этот API. Его упакованный массив записей адресов
и версий находится в управляемой памяти и имеет ёмкость полезных данных 8 + 4 байта
на ID в x64. `AccessorBufferBytes` измеряет полезные данные этого управляемого
массива без заголовков; `NativeBytes` описывает хранилище столбцов компонентов.
Это разные счётчики, и ни один нельзя подставлять вместо другого. Поэтому график
не измеряет производительность аксессора или компромисс по памяти; для этого нужны
отдельные сценарии и замеры. Перед интерпретацией различий во времени запишите
и проверьте точное происхождение исходного бинарного файла, ревизию оптимизированной
версии, бэкенд, среду выполнения, машину и дату запуска.

Результаты характеризуют указанную машину, среду выполнения, фиксированные тестовые
сценарии и правила выборок. Они не устанавливают производительность для всех
нагрузок, оборудования, Unity/IL2CPP или будущих версий библиотек. Счётчики
управляемых аллокаций не включают нативное хранилище SECS и не являются замерами
всей памяти. Усы стандартного отклонения описывают разброс выборок, а не доверительные интервалы.

## Воспроизведение

Запускайте из корня репозитория с локальным окружением matplotlib:

```powershell
$env:PYTHONPATH = (Resolve-Path Benchmarks.Local/python-packages).Path
python Benchmarks.Local/plot_optimization.py
```

По умолчанию построитель графика читает два файла свежих повторных замеров базовой
версии и два файла оптимизированной версии, названные выше, затем записывает
`docs/benchmarks/optimization.png`. Для выбора других входных данных используйте
`--base-results`, `--base-stress`, `--optimized-results` или `--optimized-stress`.
Он не изменяет JSON результатов. Достаточно результатов оптимизированной версии
только для SECS; строки других фреймворков игнорируются.

о всеобщем ускорении или статистической значимости.

### Замеры нового API

Отдельные сценарии создания инициализируют одинаковые значения Position/Velocity.
Каждый метод начинает с нового мира и подготовленного шаблона вне таймера;
создание включает рост записей и выделение чанков. Результаты при миллионе
сущностей: пустая сущность плюс два вызова Add 104.644 ms, прямое создание
с компонентами 61.671 ms, пакет подготовленной фабрики 44.207 ms
(2.37x относительно empty/Add/Add). Исходный базовый сценарий создания использует
другие данные компонентов и не должен напрямую сравниваться с этим новым сценарием.

Отдельные сценарии поиска используют один и тот же заполненный мир и перестановку
с фиксированным seed для обоих API. Они используют 256 базовых компоновок, но
не включают компонент Hot стресс-сценария и используют другой seed. Аксессор
создаётся вне измерения времени; его память остаётся выделенной при выполнении
обоих методов. Поэтому эти числа образуют пару внутри данного сценария,
а не заменяют исходные замеры RandomLookup.

| Сущности | World.Get | Кешированный Accessor.Get | Исходный / Кешированный |
| --- | ---: | ---: | ---: |
| 100,000 | ![Отставание от 30%](heatmap/worst.svg "Отставание от 30%") 0.870 ms | ![Отставание до 5%](heatmap/best.svg "Отставание до 5%") 0.487 ms | 1.79x |
| 1,000,000 | ![Отставание между 5% и 30%](heatmap/bad.svg "Отставание между 5% и 30%") 56.982 ms | ![Отставание до 5%](heatmap/best.svg "Отставание до 5%") 44.440 ms | 1.28x |

SD поиска при миллионе сущностей составляет 9.250 и 11.044 ms соответственно,
поэтому преимущество аксессора здесь недостаточно стабильно, чтобы обещать
фиксированное ускорение. Объём сохранённых полезных данных записей составляет
1.5 MiB при 100,000 ID и 12 MiB при 1,000,000 ID. Затраты на поддержку таблицы
при структурных изменениях и создание аксессора этим сценарием только поиска
не измеряются. См. [компромиссы API](../SECS_OPTIMIZATION.ru.md).

### Сохранённое нативное хранилище

Отдельная диагностика без измерения времени создаёт 100,000 сущностей и выполняет
20 проходов добавления и удаления в перемешанном порядке с полезной нагрузкой
256 байт, проверяя оставшиеся данные после каждого прохода. Она читает одинаковые
внутренние поля чанков и шага размещения в обеих средах выполнения через
рефлексию, что позволяет исполняемому файлу работать с исходной DLL.

память и накладные расходы нативного аллокатора. Диагностические JSON находятся
в `storage-baseline.json` и `storage-optimized.json`.

### Проверка

- 15 модульных тестов проходят в Debug и Release, включая фактическое удаление
  с перемещением последней сущности при миграции и уничтожении, проверки поколений
  аксессора, освобождение ресурсов, локальную для мира регистрацию, создание
  по шаблону и границы хранилища за 20 циклов.
- 8 базовых и 14 стресс-сценариев измерены на исходной и оптимизированной средах
  выполнения. Все стресс-сценарии проверяют полное состояние сущностей после измеряемых операций.
- Небольшие граничные стресс-сценарии (257 и 4,097 сущностей) проходят все семь
  сценариев с тремя повторениями, а также цикл добавления и удаления полезной нагрузки.
- Все 10 сценариев замеров нового API проверяют контрольные суммы и данные вне измерения времени.
- Быстрая проверка BenchmarkDotNet в режиме in-process Dry завершается для всех
  10 сценариев нового API. Это проверка выполнения, а не источник сравнительных замеров выше.
- Проверка жизненного цикла OtherBenchmarks проходит 43 класса и 172 цикла.
- Количество выборок, средние значения и выборочные стандартные отклонения
  пересчитаны из сохранённых массивов. Итоговый парный график построен и проверен визуально.
