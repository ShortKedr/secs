# Техническое задание: подготовка первого релиза SECS

Статус: задание на реализацию, **не подтверждение готовности**. Первый планируемый
релиз — `SECS v0.1.0 — Cone`; дата в названии ставится только в день публикации.
Правила последующих версий описаны в [документе о версиях](VERSIONING.ru.md).
Исторический срез блокеров записан в
[отчёте от 2026-10-14](RELEASE_READINESS_2026-10-14.ru.md);
итоговая приёмка требует нового отчёта для точного релизного коммита.

## Цель и границы

Получить библиотеку, которую разработчик может установить из артефактов GitHub
Release в обычное C#-приложение, проект Unity и проект Godot C#. Коммит и тег
однозначно определяют исходники, версию бинарников, пакет и примечания к релизу.
Сборка и проверки пакета автоматизируются; проверки Unity для первого релиза
выполняются локально на отдельных копиях тестового проекта. Публикация
допускается только после отчёта для точного релизного коммита.

В релиз входит **ядро `SECS/`**, документация для потребителя, лицензия и
иллюстрация Cone. Space Battle, тесты, бенчмарки и содержимое
`Benchmarks.Local/vendor` не входят в распространяемую библиотеку. Это не
задание на Fixed, SIMD, многопоточность, GPU или публикацию пакета на NuGet.org.
Отдельное решение о NuGet.org можно принять после готовности GitHub Release.

## Исходное состояние и блокеры

На 2026-10-14 `SECS.csproj` собирается только для `net8.0`; без настроек
`dotnet pack` присваивает пакету `1.0.0` и шаблонное описание. Отдельного CI
библиотеки и релизного workflow нет. Локальный запуск `SECS.Tests` завершался
таймаутом подключения `testhost`, поэтому результат тестов для релиза не
подтверждён. Обложка `docs/branding/releases/cone.png` и политика версий
подготовлены локально, но релизного тега и GitHub Release ещё нет. До начала
публикации нужно определить состав коммита и синхронизировать ветку, сохранив
посторонние незакоммиченные изменения.

## Поддерживаемые потребители

«Любые приложения .NET» нельзя гарантировать буквально. Для `0.1.0` требуется
явная матрица минимальных версий и проверенных режимов:

| Потребитель | Требуемый результат | Доказательство |
| --- | --- | --- |
| .NET 8 и более новые поддерживаемые SDK | Установка локального `.nupkg`, компиляция и запуск примера без ссылки на исходники | Пустое приложение-потребитель в CI для .NET 8; сборка на следующей поддерживаемой версии SDK |
| .NET Framework 4.8 на Windows | Установка пакета и запуск того же базового сценария через совместимую сборку | Отдельный Windows smoke test |
| Unity 2022.3 LTS и Unity 6 | Импорт готовых DLL, создание мира, запрос, освобождение памяти | Минимальный проект, запуск в Editor/Mono и Player/IL2CPP на одной указанной платформе для каждой поддерживаемой ветки |
| Godot 4.5 .NET, desktop | Подключение локального `.nupkg`, сборка и запуск сцены с созданием мира и запросом | Минимальный C#-проект, запуск Godot .NET на desktop |

Для широкой совместимости исследовать сборку `netstandard2.0` вместе с `net8.0`.
Текущий код использует `CollectionsMarshal.AsSpan` и `Unsafe`, поэтому простая
смена `TargetFramework` без адаптации и проверки недопустима. Совместимые
сборки должны сохранять одну публичную семантику; оптимизация только для .NET 8
не должна менять результат. Если `netstandard2.0` невозможен без существенного
изменения ядра, зафиксировать причину, измерения и новую матрицу **до**
объявления поддержки Unity или .NET Framework. Не заявлять поддержку платформ,
для которых есть только компиляция, но нет соответствующего запуска. WebGL Unity,
мобильные экспорты и Godot C# Web не входят в матрицу `0.1.0`.

## Артефакты и метаданные

1. Единственный источник версии для сборки и упаковки; для релиза значения в
   исходниках, NuGet metadata, DLL и теге `secs-v0.1.0` должны совпадать.
   CI отклоняет тег с иной версией. Дата и имя Cone не входят в числовую версию.
2. Пакет `.nupkg` содержит только сборки ядра для заявленных target frameworks,
   корректные зависимости, README установки, `MIT` license expression,
   авторство, описание, URL репозитория и исходного коммита. Никаких шаблонных
   полей `Package Description` и случайной версии `1.0.0`.
3. Для Unity подготовлен отдельный ZIP с совместимыми DLL и всеми необходимыми
   зависимостями, `LICENSE`, краткой инструкцией импорта и точным списком
   проверенных Unity/backend версий. Если пакет не имеет зависимостей, это
   должно подтверждаться содержимым сборки и манифеста, а не предположением.
4. GitHub Release содержит `.nupkg`, Unity ZIP, SHA-256 для артефактов,
   `verification-0.1.0.json` и `cone.png`. Отдельные `.snupkg`/символы добавляются при готовой проверенной
   процедуре, но не должны задерживать саму библиотеку.
5. Исходники остаются доступными через релизный тег. Содержимое `.nupkg` и ZIP
   проверяется распаковкой: в них нет Space Battle, стороннего vendor-кода,
   временных файлов и результатов бенчмарков.

Имя пакета должно быть окончательно выбрано и проверено на конфликт перед
публикацией (`SECS` — лишь текущее имя проекта, не доказательство доступности
имени на внешнем feed). Для GitHub Release достаточно локально устанавливаемого
`.nupkg`; выкладка на NuGet.org требует отдельного решения и учётных данных.

## Проверки и публикация

**Проверка PR и `main`.** Отдельный workflow для SECS с минимальными правами
`contents: read` собирает все заявленные target frameworks, выполняет
`SECS.Tests`, `dotnet pack`, проверку пакета и доступные на GitHub-hosted
runners smoke tests потребителей. Падение тестового хоста и пропуск проверки
не считаются успехом. Unity не требует постоянного self-hosted runner для PR:
её релизная матрица проверяется локально перед выпуском.

**Локальный отчёт релизного кандидата.** Проверки выполняются из чистого
рабочего дерева на точном коммите, из которого собраны `.nupkg` и Unity ZIP.
Один JSON-файл `verification-0.1.0.json` содержит версию, полный SHA коммита,
дату, ОС, точные версии SDK/Godot/Unity и backend, статусы `passed` / `failed` /
`not_run`, пути к логам и SHA-256 каждого распространяемого файла. Если рабочее
дерево не было чистым, статус проверки не подтверждён или SHA-256 не совпал,
`releaseReady` равен `false`. Для Unity используются новые Editor-процессы с
отдельными копиями тестового проекта внутри этого репозитория.

**Публикация.** Только после полного локального отчёта создаётся тег
`secs-v0.1.0` на проверенном коммите `main`. Перед публикацией сверяются
версия, лицензия, содержимое артефактов и контрольные суммы. В GitHub Release
прикрепляются пакет, Unity ZIP, обложка, SHA-256 и JSON-отчёт; примечания
содержат только реально проверенные платформы. Существующий релиз и тег не
перезаписываются. После публикации файлы скачиваются и проверяются заново.
Автоматический релизный workflow можно включить позднее, когда он будет
согласован с этим локальным источником доказательств.

**Название и обложка.** Заголовок: `SECS v0.1.0 — Cone · YYYY-MM-DD`, где
`YYYY-MM-DD` — фактическая дата публикации. `cone.png` прикрепляется как asset
и отображается в начале примечаний через ссылку на этот asset. В тексте:
краткое описание возможностей, установка для .NET/Unity/Godot, матрица
проверенных версий, ограничения текущего API, изменения, лицензия, проверки,
контрольные суммы и ссылка на точный тег. `0.1.0` — первый ранний API, без
обещания стабильности `1.0.0` или ещё не реализованных возможностей.

## Приёмка перед первым выпуском

- `dotnet test` проходит повторяемо на чистом релизном коммите. Сборки для
  разных target frameworks проходят без ошибок; для каждого
  заявленного потребителя есть исполняемый smoke test, а не только проектный
  файл. Ограничения платформ документированы.
- Контрольный потребитель устанавливает **собранный `.nupkg`** и выполняет
  `CreateEntity → Query → Get → Dispose`; Unity и Godot используют именно
  релизные бинарники. Проверены требования к `unsafe` и IL2CPP.
- Распакованный `.nupkg` имеет версию `0.1.0`, нужные TFM, корректные metadata,
  README и лицензию. ZIP Unity содержит ровно проверенный комплект.
- Отчёт `verification-0.1.0.json` содержит только подтверждённые результаты
  для точного релизного коммита; нет обязательных `failed` или `not_run`.
  SHA-256 опубликованных файлов совпадают с отчётом, DLL и пакет получены из
  коммита релизного тега.
- GitHub Release существует, доступен по тегу `secs-v0.1.0`, содержит все
  артефакты, видимую обложку и инструкции, проверенные скачиванием и
  установкой после публикации. Релиз не считается готовым по одному только
  успешному созданию тега или черновика.

Если любой пункт не выполнен, выпуск останавливается с конкретным отчётом:
какая проверка не прошла, на какой платформе, лог/артефакт и требуемое
исправление. Публикация не должна автоматически обходить упавший gate.

## Порядок работ

1. Закрепить матрицу поддержки и добиться совместимых сборок ядра; проверить
   поведение в настоящих потребителях. При необходимости скорректировать
   заявленный минимум платформ до релиза.
2. Настроить версию и метаданные, собрать/распаковать пакет и Unity ZIP,
   написать инструкции установки и release notes.
3. Добавить CI проверки пакета без обязательного self-hosted runner;
   локально выполнить все сценарии потребителей, включая Unity Editor/Mono/IL2CPP.
4. Сверить состав рабочего дерева, зафиксировать `0.1.0`, собрать артефакты из
   чистого коммита и заполнить JSON-отчёт; затем создать тег и GitHub Release.
5. Скачать файлы с опубликованной страницы и повторить установку в чистых
   потребителях; сохранить ссылки и результаты как свидетельство приёмки.
