# Правила разработки GA систем SECS

Дата: 2026-10-12  
Статус: нормативный subset v1, редакция требований 0.2 после исследования SpaceGame; реализации нет.

Этот документ задаёт правила для авторов и инструментов, которые будут добавлены вместе с Graphics Accelerated (GA) execution. Он не описывает существующий API и не означает, что система уже переносится на GPU. Архитектурный контракт см. в [спецификации](SPEC.ru.md), последовательность работ — в [плане реализации](IMPLEMENTATION_PLAN.ru.md), конкретные требования игры — в [исследовании SpaceGame](SPACEGAME_REVIEW.ru.md).

Термины «обязан», «запрещено» и «допускается» нормативны для целевого GA-профиля. До реализации это требования к проектированию и будущим проверкам.

## 1. Цели и область действия

1. Одна GA-система задаёт одну семантику симуляции для CPU и GPU исполнителей.
2. Переносимая система имеет один авторский исходник C#; генератор может создавать CPU и GPU представления из него.
3. Доступность GPU меняет исполнитель и стоимость, но не значения состояния, события, команды, идентификаторы или конечный результат тика.
4. Классификация «GPU portable» означает поддержку проверенным компилятором и backend. Она не означает поддержку каждого устройства или API.
5. В первой версии общим целевым набором является небольшой профиль числовых операций, а не произвольное выполнение C#.
6. Правила применяются к транзитивно достижимому коду системы: `Execute`, вызываемые методы, операторы, свойства, generic специализации и константные данные.
7. Система, которая не проходит правила детерминизма или безопасности записей, не становится допустимой через выбор CPU fallback.
8. Legacy API SECS сохраняет текущее поведение. GA включается явно при сборке; обычные `ForEach`, `Chunks`, `AddSystem`, `Run` и `RunAll` не преобразуются неявно.
9. Эти правила не переводят SpaceBattle, стороннюю физику либо существующие float-системы в GA автоматически.

## 2. Явное включение и исполнитель

1. Предлагаемый build property — `SECSGraphicsAccelerated=true`. Это проектное имя; до утверждения спецификацией оно не является существующей настройкой SDK.
2. Включение свойства разрешает анализ GA-кода и генерацию GA артефактов. Оно не требует наличия GPU при сборке или запуске.
3. GA-сборка обязана выдавать отчёт о найденных системах, их классификации и версиях правил/генератора.
4. При запуске выбор GPU либо CPU делается только среди исполнителей, которые поддерживают объявленные возможности конкретного этапа.
5. CPU fallback допускается для системы из категории «CPU fallback safe» и обязан сохранять её зафиксированный контракт.
6. `RequireGpu` для этапа означает, что CPU fallback для этого этапа запрещён. Если подходящего GPU backend нет, выбор плана завершается ошибкой до первого тика. Host orchestration и общий CPU structural commit не считаются fallback вычислительного kernel.
7. Система не должна узнавать выбранный backend через изменяемое глобальное состояние и ветвить симуляционную семантику.
8. Backend может менять разбиение работы, память, передачу данных и число проходов только при доказанном совпадении результата.
9. Переход на другой исполнитель во время уже начатого dispatch запрещён.

## 3. Предлагаемая форма системы

Целевой исходник объявляет partial struct с атрибутом системы и однозначной точкой входа. Схематичный пример ниже задаёт только ожидаемую форму, а не готовый API:

```csharp
[SecsSystem]
public partial struct IntegrateMotion
{
    public void Execute(Entity e, ref Position p, in Velocity v)
    {
        p.X = p.X + v.X;
        p.Y = p.Y + v.Y;
    }
}
```

1. `Entity` является входом для адресации, журналирования и формирования стабильного ключа команды. Его CLR-представление не обязано совпадать с GPU форматом.
2. Компоненты и типы значений должны быть доступны генератору как закрытый набор полей фиксированной схемы.
3. `ref` обозначает разрешённую запись в собственную сущность и компонент; `in` обозначает чтение.
4. Передача компонента по значению допускается только для утверждённого portable value type.
5. `Execute` не может сохранять ссылки, указатели, `Span`, ref-struct или адреса компонент за пределами вызова.
6. Вызов системы не получает скрытый `World`, `Battle`, глобальный registry, scheduler, произвольный delegate или динамический service locator. Разрешён явный scoped `SystemContext`, понижаемый в объявленные buffers/handles, а не произвольный managed object.
7. Фактическое имя атрибута, сгенерированная сигнатура и поддержка дополнительных overloads будут закреплены в SPEC и реестре поддерживаемого подмножества.
8. Изменение формы исходника требует обновить реестр, анализатор, генератор, спецификацию и проверки в одном согласованном изменении.

Для игровой системы предлагается `Execute(in SystemContext context, Entity entity, ref Inventory inventory, ref Hull hull)`. Контекст предоставляет зарегистрированные Own/Has/TryRead/ReadSnapshot/Resource/Emit/Commands operations. Дополнительные own Shield/Heat и optional tags объявляются в access descriptor; ctx.Own не возвращает ref для соседней сущности. Query membership и access requirements различаются: отсутствующий required компонент даёт определённый fault, а не молча исключает сущность из query.

Tick, Config, seed и catalogs передаются как frozen typed resources. AiRows/parent/cell buffers имеют schema, bounds и lifetime; host preparation может использовать List/Dictionary, но kernel получает только зарегистрированный view. Borrowed Span из host list нельзя удерживать через dispatch; lazy cache Ready flags не разрешают скрытые shared writes. Counters/Tactics оформляются contributions с заданным merge. Реальный processor с полем Battle не считается переносимым без выражения этих доступов через контекст.

## 4. Поддерживаемые типы и арифметика

### 4.1 Типы первой portable-поверхности

1. Примитивный профиль включает `bool`, enum, `int` и `uint` с каноническим представлением в 32 бита.
2. `bool` в ABI хранится как канонические 32-битные `0` или `1`; любые другие входные значения считаются некорректной схемой.
3. Enum имеет явный поддерживаемый underlying type и сериализуется как соответствующее каноническое 32-битное целое. Неизвестные значения enum не получают неявной нормализации.
4. `long`, `ulong` и `Fixed` допускаются только через точное пооперационное lowering в пары 32-битных слов либо доказанную backend-инструкцию с теми же правилами.
5. Если точный GPU lowering недоступен, такая система классифицируется как CPU fallback safe только при наличии точного CPU lowering. Аппаратная 64-битная операция не является обязательным требованием к GPU.
6. Для будущего `Fixed` применяется контракт [общей числовой задачи](../prompts/03_FIXED.ru.md): signed Q32.32, nearest ties-to-even, OverflowException независимо от checked контекста, DivideByZeroException и достаточная промежуточная разрядность. GPU сообщает тот же вид fault через host boundary; throw/catch внутри kernel не требуется. Конкретная версия правил должна совпадать с числовым API.
7. `Int128` может использоваться как логическая ширина промежуточного результата. Требование не означает, что GPU обязан иметь нативный тип `Int128`.
8. Если точный переносимый результат нельзя получить без переполнения промежуточного вычисления или потери разрядов, система должна получить диагностику, а не перейти к приблизительной операции.

Для int/uint/long/ulong сохраняются явно заданные C# checked/unchecked правила. Unchecked arithmetic/casts работают modulo 2^N, checked дают fault. Signed division округляет к нулю, remainder имеет знак делимого. SECS фиксирует fault для деления на ноль и signed MinValue / -1 либо MinValue % -1 в обоих contexts. Shift count маскируется 31 или 63, signed right shift является арифметическим. Целевой shader язык не может подменить это своим undefined behavior; правила соответствуют SPEC.

### 4.2 Начальный синтаксис

| Конструкция | Правило v1 |
| --- | --- |
| Локальные значения, присваивание, compound assignment | Разрешены для зарегистрированных типов, с явной числовой семантикой |
| if, conditional expression, switch по integer/enum | Разрешены при наличии соответствующего IR lowering; short-circuit и evaluation order сохраняются |
| for и ограниченные while, break/continue | Допускаются с проверяемой конечной верхней границей по константе или замороженному входу; неизвестный лимит не скрывается fallback |
| Struct fields, known value helpers, properties/operators | Проверяется весь достижимый код; getter не считается чистым только по названию |
| Generic методы | Только закрытые специализации утверждённых типов |
| Fixed-size данные и индексирование | Только зарегистрированный value/buffer API со schema, bounds checks и известным layout |
| InlineArray и nested value structs | Фиксированная длина и явная schema; InventoryItems[16] является обязательным CPU/GPU ABI fixture |
| Scoped SystemContext и resource views | Только registered intrinsic operations и declared own/optional/snapshot accesses; mutable World не передаётся |
| ref/in и aliases | Только разрешённый доступ текущего вызова; escaping refs и запись в чужую сущность отклоняются |
| throw/catch, recursion, await, yield, LINQ, dynamic CLR dispatch | В начальный portable subset не входят |

Таблица задаёт целевую поверхность v1; compiler registry отражает реализованное покрытие каждой конструкции. Разрешённая и проверенная CPU операция без готового GPU lowering даёт явный safe fallback. Семантически неизвестная форма остаётся ошибкой.

### 4.3 Запрещённая арифметика первой версии

1. `float` и `double` не допускаются в значимых для симуляции полях GA-профиля первой версии.
2. Незарегистрированные `Math`/`MathF`, обычная floating-point тригонометрия, преобразования с зависящим от платформы округлением и скрытые floating-point конверсии запрещены. Точный integer helper разрешается только через проверенную реализацию или intrinsic registry.
3. Запрещены epsilon-сравнения как замена точного контракта и любые backend-ветви, выбирающие разные числовые формулы.
4. Преобразование Fixed/целых значений во float для визуализации выполняется за границей GA kernel в слое presentation.
5. Добавление float-профиля потребует отдельной версии семантики и доказательств точного поведения. Наличие GPU float controls само по себе не даёт такой гарантии.

Для будущего AdvancedGameMath отдельно определяются normalize/sqrt/trig/atan2/angle wrap, damping, quadratic roots и conservative bounds. Сейчас их употребление в float SpaceGame не даёт portable статус. Новая deterministic numerical model может иметь иной checksum, чем legacy float; обе версии сравниваются в пределах своего контракта. Общая базовая задача Fixed не расширяется этим правилом автоматически.

## 5. Чистота и замыкание кода

1. Все транзитивно вызываемые методы должны быть доступны анализатору и генератору.
2. Каждый helper, property accessor и operator проверяется по тем же ограничениям типов, арифметики, памяти и побочных эффектов, что и `Execute`.
3. Generic методы разрешаются только после специализации с конкретными типами. Открытая generic цель не может быть скомпилирована как portable система.
4. Вызов библиотеки допустим только если её реализация доступна для анализа или метод отдельно сертифицирован как intrinsic с версией и точным контрактом.
5. Неизвестный helper, внешний assembly без manifest, неразрешённый virtual dispatch либо reflection не считаются безопасными по умолчанию.
6. Система не использует managed object references, строки, массивы переменной структуры, boxing, allocation, exception flow, virtual/interface dispatch, reflection, delegates или динамическую генерацию кода.
7. Запрещены `unsafe`, указатели и произвольное чтение/запись памяти, включая сырой доступ к layout компонентов.
8. Запрещены часы, wall-clock или frame delta, `System.Random`, platform RNG, процессные глобальные генераторы, незафиксированный seed и недетерминированный внешний ввод.
9. Входные параметры фиксируются на границе логического тика и входят в его replay/manifest. Нельзя повторно опрашивать внешнее состояние между частями одного тика.
10. Статические mutable поля, thread-local данные и скрытое состояние worker запрещены.
11. Константы имеют фиксированный тип и сериализуемое значение; culture-sensitive parsing/formatting не является допустимым способом получить значение kernel.
12. Вызов неизвестного метода даёт диагностику с цепочкой вызовов до исходного места, а не молча классифицируется как fallback.

## 6. Модель данных и запись

1. Внутри одной системы чтение выполняется из snapshot состояния, зафиксированного перед запуском этой системы.
2. Запись в собственную сущность через разрешённый `ref` формирует логическое next-state; следующий read собственного поля видит последнюю локальную запись. Это не требует двойного хранения всего World. Отдельный неизменяемый snapshot нужен для соседних чтений одновременно записываемого типа.
3. Соседние сущности читаются из snapshot. Порядок обработки сущностей не меняет данные, которые видит другая сущность в том же этапе.
4. Запись в компонент соседа запрещена, если она не объявлена отдельным детерминированным механизмом событий или редукции.
5. Прямое пересечение записей двух логических задач не допускается, даже если текущий GPU запускает их последовательно.
6. Повторные записи одной задачи в собственное поле выполняются строго по исходному порядку операций.
7. Временные параметры, система инициализации, начальные значения и граница snapshot входят в описание work stage.
8. Сохраняемые chunk pointers, entity row indices и физические индексы worker не являются стабильными ключами симуляции.
9. Порядок обхода storage может различаться. Система обязана давать тот же результат независимо от размера чанка и физического порядка задач. Default semantic source order — Entity ID/generation; допустим versioned domain descriptor, например Serial. Переиспользованный Entity ID не заменяет игровой Serial.
10. Система не должна зависеть от padding, неинициализированных байтов, `GetHashCode`, адресов памяти или порядка layout, не включённого в schema.

Snapshots/resources обновляются на BeginTick и согласованной границе стадии. Допустимая внешняя запись через ref после Completed должна быть видна следующему тику; счётчик вызовов Set не достаточен для dirty-range cache. Пока write tracking не доказан, применяется полный refresh. Renderer/observer/Web diagnostics не читают live World в Pending.

Spatial query объявляет candidate/exact, multiset/unique semantics, output order, conservative bounds и outside/large fallback. Traversal клеток не задаёт выбор цели при равном score. GPU consumer получает typed buffers; неинициализированные/stale query epochs и отсутствие candidates из-за clipping являются ошибками. Fixed query использует своё определённое raw outward rounding; legacy nextafter/nonfinite поведение не заменяется произвольным epsilon.

## 7. События, команды, ID и редукции

1. GA-система не выполняет немедленные структурные операции над World во время обхода.
2. Создание, уничтожение, добавление и удаление компонента выражаются через буферизированные команды следующей границы commit.
3. Default каждая команда получает ключ общего runner (tick, stage, systemOrder, sourceKind, sourceId, sourceGeneration, localOrdinal). SourceKind=0 для сущности с ID/generation; sourceKind=1 для logicalJobId с sourceGeneration=0. LocalOrdinal является общим commands/events счётчиком одного источника. Grouped stream может объявить domain order descriptor (Serial, Slot), (Serial, Kind, Enable), (Team, Order) после commitGroup prefix и перед полным tie-break (producerOrder, sourceKind, sourceId, sourceGeneration, localOrdinal). Такое объединение kernels фиксируется в SPEC; скрытые дополнительные поля порядка запрещены.
4. Упорядочивание команд задаётся каноническим порядком ключей, а не порядком завершения потоков, GPU workgroup, атомарной операции или очереди драйвера.
5. Создание возвращает ticket ключа Create; новые entity IDs выдаются на semantic commit barrier после канонической сортировки commands. В первом выпуске на ticket ссылаются только последующие commands того же источника с большим localOrdinal, без обмена между источниками до commit. Любой domain descriptor сохраняет Create-before-use. GPU lane не резервирует игровой ID напрямую.
6. Версия и повторное использование ID подчиняются одной политике на CPU и GPU. Переполнение версии должно иметь явную политику.
7. События имеют явный schema, источник, локальный ordinal и детерминированный порядок публикации.
8. Событие не может быть потеряно, повторено либо видимо раньше commit из-за backend или размера batch.
9. Редукции задают операцию, начальное значение, порядок/дерево свёртки и правила overflow. Если любое дерево неэквивалентно для выбранной арифметики, требуется фиксированное дерево или иной точный контракт. Ordered apply является отдельным режимом: Shield/plasma/LastAttacker/death из последовательного Damage не заменяются суммой или atomic add.
10. Неподдерживаемые атомарные операции запрещены. Атомик не становится детерминированным лишь потому, что предотвращает гонку памяти.
11. Командный buffer имеет явную ёмкость и политику превышения. Нельзя молча отбрасывать хвост или менять порядок событий при переполнении. Игровой лимит MaxProjectiles/team/home может отвергать request по правилам игры: принятие/отказ и порядок распределения воспроизводятся; это не скрытая потеря данных backend.
12. Commit выполняется после завершения standalone logical системы либо объявленного CommitGroup и всех требуемых backend barriers. Producer kernel внутри группы может завершиться без structural commit; его component writes и snapshot epochs имеют явно заданную видимость. Grouped streams могут объединять requests из нескольких kernels до общего OrderedApply, как shots/state requests в игре.

Particles и иные VFX считаются presentation только после анализа зависимостей. Shared serial/allocator/RNG или влияние на следующий spawner делает соответствующие allocation events significant. Освобождение таких events от replay изменяет правила и требует отдельной версии.

## 8. Классификация и решения

Каждая система получает ровно одну классификацию для конкретной версии компилятора и backend.

| Класс | Значение | Решение при запуске |
| --- | --- | --- |
| GPU portable | Код и schema принадлежат проверенному подмножеству; есть валидный lowering для выбранного backend | GPU либо детерминированный CPU fallback, если этап не требует GPU |
| CPU fallback safe | GPU lowering отсутствует, но известный CPU маршрут соблюдает те же детерминированные правила и запись без конфликтов | CPU; ошибка при `RequireGpu` |
| Ошибка | Нарушен контракт детерминизма/записей либо семантика неизвестна | Сборка/анализ блокируется |

1. «Не GPU portable» само по себе может привести к CPU fallback лишь после проверки допустимости всего исходника.
2. Fallback не разрешает гонки, неизвестные побочные эффекты, плавающую арифметику или неопределённый порядок.
3. Неизвестный intrinsic, внешний helper, memory alias, конфликт записей и неподдерживаемая команда получают ошибку до запуска.
4. CPU fallback исполняет ту же математическую и событийную семантику, а не альтернативный алгоритм.
5. Для stage с `RequireGpu` невозможность GPU lowering считается ошибкой конфигурации при выборе плана до первого тика.
6. Отчёт сборки и runtime обязан перечислять причину fallback, выбранный исполнитель и фактически запущенный backend.

Registered CPU stage/service объявляет Read/Write, numerical version, significant state и continuation. SnapshotPreparation и OrderedApply могут постоянно исполняться на CPU в общем plan. Числовая корректность этих стадий проверяется столь же строго: текущий float circle PhysicsService, хотя он собственный, не становится deterministic fallback автоматически. Непроверенный legacy stage остаётся вне full-game parity claim.

## 9. Диагностики и ошибки исполнения

Предлагаемые диагностические идентификаторы стабильны после публикации, а их названия и область применения должны быть закреплены в analyzer registry.

| ID | Нарушение | Начальное действие |
| --- | --- | --- |
| GA0001 | Тип или layout вне portable schema | Ошибка |
| GA0002 | Недетерминированная арифметика или преобразование | Ошибка |
| GA0003 | Managed state, allocation или запрещённая CLR-функция | Ошибка |
| GA0004 | Неизвестный transitive helper или intrinsic | Ошибка с цепочкой вызовов |
| GA0005 | Запись пересекает сущности или задачи | Ошибка |
| GA0006 | Нестабильная команда, событие, ID или редукция | Ошибка |
| GA0007 | Нет GPU lowering; допустимый CPU маршрут подтверждён | Информация о fallback |
| GA0008 | Требуемый GPU исполнитель недоступен для stage | Ошибка выбора |
| GA0009 | Manifest/schema/backend ABI несовместим | Ошибка загрузки |
| GA0010 | Переполнен буфер команд/событий | Ошибка этапа, без молчаливой потери |

1. Сообщение диагностики указывает место источника, конкретное правило, цепочку helper-ов и предлагаемую категорию решения.
2. Уровень severity нельзя понизить до предупреждения для ошибок, которые могут менять симуляционный результат.
3. Неподдерживаемое свойство не исчезает через предупреждение, pragma suppression или автогенерацию приблизительной замены.
4. Запросы подавления диагностики допускаются только для шумовых сообщений, не для нарушений контракта.
5. Ошибка до запуска stage не должна оставлять World частично изменённым.
6. Ошибка во время dispatch переводит runner в `Faulted`; он выполняет drain связанных задач и device submissions, не публикует Completed и не выполняет прозрачный повтор на CPU. Безопасное освобождение GPU буферов требует подтверждения окончания их использования.
7. Частичная запись рабочего World после ошибки не считается автоматически откатанной. Восстановление выполняется только по отдельному явно определённому checkpoint/recreate контракту.
8. Ошибка driver/device loss не даёт права перезапустить тот же тик с CPU поверх частично изменённого состояния.

Первый арифметический fault выбирается по (tick, stage, systemOrder, kernelOrder, sourceOrderOrdinal, evaluationOrdinal), как в SPEC. KernelOrder равен нулю для standalone системы. SourceOrderOrdinal задаётся canonical/domain descriptor с sourceKind до dispatch; Entity ID/generation остаются в payload. EvaluationOrdinal учитывает фактические повторения loop и C# evaluation order. Source ID сообщает строку, но не заменяет порядок. CPU и GPU fault payload сравниваются независимо от частично изменённого закрытого рабочего состояния.

Checkpoint для восстановления включает allocator/generations, значимые resources/queues/RNG и state CPU services. Render frame и Battle.Checksum сами по себе не являются этим checkpoint. Rebuildable caches отдельно проверяются restore/continue; контактная history, влияющая на begin-contact и damage, не исключается из significant state. Body slots/free IDs сервиса и PhysicsLink.Body сохраняются либо восстанавливаются с проверенным remap; raw physical handle исключается только по явной logical-handle schema.

## 10. Версионирование поддержки

1. Версия поддерживаемого подмножества закрепляет типы, операции, вызовы, layout, команды и диагностические правила.
2. Версия analyzer, IR/lowering, ABI, manifest и backend capability перечисляется в отчёте сборки и в записи replay.
3. Изменение семантики Fixed, enum/bool representation, порядка редукции, командного ключа или ABI требует изменения версии контракта.
4. Новая операция сначала появляется в реестре с точной спецификацией и только затем включается в генератор.
5. Обратная совместимость языка и бинарного manifest проверяется отдельно; наличие одинакового имени системы не означает совпадение семантики.
6. Backend capability manifest перечисляет поддерживаемые типы, операции, лимиты buffer, barrier-модель и проверенные версии runtime/API/driver.
7. Незаявленная комбинация устройства, runtime, API или driver считается непроверенной и не выдаёт подтверждение GPU parity.

## 11. Требования к проверкам изменения языка

Каждое изменение подмножества языка сопровождается всеми следующими видами проверки:

1. Положительный compile case на каждый новый разрешённый синтаксис и его transitive helper.
2. Отрицательный compile case для ближайших запрещённых форм, включая обход через property, operator, generic specialization и external helper.
3. Проверка стабильности ID и текста диагностики, диапазона source location и цепочки вызовов.
4. CPU reference и минимум один GPU backend запускают одинаковые входы и сравнивают каноническое состояние после каждого тика. Для gameplay поддержаны SG 01–06 из плана; один Movement не закрывает extra accesses/resources/events.
5. Проверяются повторные процессы, разные размеры chunk/batch, порядок завершения задач, разные backend widths и повторное использование entity IDs.
6. Для арифметики используются независимый эталон и границы диапазона, отрицательные значения, halfway, переполнение и сериализация.
7. Для событий/команд проверяются конфликтующие ключи, каноническая сортировка, лимит buffer и идентификаторы, назначенные после commit.
8. Сравнивается схема каждого определённого поля; raw memory, padding и runtime hash не являются эталоном.
9. Принудительный `RequireGpu` тестируется на среде с GPU и на среде без нужной capability. Второй случай обязан завершиться ошибкой, а не зелёным CPU результатом.
10. Неподдерживаемая система отдельно демонстрирует диагностируемый CPU fallback; тот же source с нарушением детерминизма обязан блокироваться.
11. Любая намеренная смена goldens версионирует контракт и проверяется отдельно; сравниватель не переписывает их автоматически.
12. Только проверенный backend/device набор попадает в поддерживаемую матрицу. CPU архитектурная матрица не заменяет GPU проверку.

Дополнительно проверяются source Serial против reused Entity ID, same-score ties, accepted/rejected capacity, duplicate state requests, InlineArray bounds, external ref edits, parent destruction, query multiset/unique и восстановление service history. Host lane проверяет Pending/Completed при pause/reset, а Web — поколение view при замене опубликованного buffer. Whole-game гарантия появляется только после qualification всех significant стадий.

## 12. Практический чек-лист автора

Перед объявлением системы GA-совместимой автор отвечает «да» на каждый применимый пункт:

- [ ] Все входы тика фиксируются до запуска и имеют явную schema.
- [ ] Все компоненты состоят из утверждённых типов, фиксированных полей и канонического layout.
- [ ] Каждая достижимая функция видима анализатору или зарегистрирована с точной версией и контрактом.
- [ ] Числа используют только разрешённые операции и единые правила округления/overflow.
- [ ] Нет float-пути, внешнего времени, случайности, managed состояния и непроверяемых побочных эффектов.
- [ ] Записи ограничены собственной сущностью; соседние чтения используют snapshot.
- [ ] Структурные изменения, события и редукции выражены декларативными deterministic commands.
- [ ] Порядок и назначение ID не зависят от lane, worker, batch или фактического порядка завершения.
- [ ] Выбрана честная категория: GPU portable, CPU fallback safe либо ошибка.
- [ ] Для `RequireGpu` определён и проверен backend, а fallback явно запрещён.
- [ ] Положительные/отрицательные компиляционные примеры и differential replay обновлены.
- [ ] SPEC, implementation plan и registry используют одну версию и одну формулировку контракта.

Если хотя бы одно свойство неизвестно, автор не помечает систему как portable. Сначала уточняется контракт или добавляется проверяемая возможность; неопределённость не заменяется предположением о последовательном выполнении.
