# Развитие фреймворка SECS

План от 12 октября 2026 года охватывает переносимый SIMD, выполнение одного логического тика за несколько кадров, детерминированную арифметику Fixed и детерминированную многопоточность. Основная реализация относится к `SECS/SECS.csproj` в `SECS.sln`. Изменения остальных проектов, включая тесты и бенчмарки, перечислены отдельно в [сопутствующих изменениях](RELATED_CHANGES.ru.md).

Это план реализации. Приведённые гарантии являются требованиями к будущим изменениям. Текущий API описан в [руководстве библиотеки](README.ru.md), реализованные оптимизации — в [отдельном документе](../SECS_OPTIMIZATION.ru.md). Fixed, time slicing, SIMD kernels и параллельный runner в текущем ядре ещё отсутствуют.

[Карта документации](../README.ru.md) · [Внутренние шаблоны задач](prompts/README.ru.md)

## Принятые ограничения

- Time slicing продолжает один логический тик за несколько кадров. Следующий тик начинается после полного завершения текущего.
- Для числового типа допустимы 8 байт. Рабочий профиль этого плана — signed Q32.32; его диапазон необходимо проверить на сценариях пользователей библиотеки.
- Менять можно только файлы текущего проекта. Запрещены изменения удалённых состояний и записи в Miro.
- Существующие изменения в рабочем дереве сохраняются. Основные промпты не включают доработки SpaceBattle.
- Новые возможности подключаются явно. Существующие `ForEach`, `Chunks`, `AddSystem`, `Run` и `RunAll` сохраняют своё поведение.

## Текущая архитектура

SECS использует .NET 8 и unmanaged-компоненты. [Archetype.cs](../../SECS/Archetype.cs) хранит отдельную непрерывную колонку каждого типа компонента в чанке: смещения рассчитываются по размеру типа и ёмкости чанка. Это SoA между типами компонентов, но поля внутри `Position { X, Y }` остаются AoS. Нельзя считать все X непрерывной колонкой.

[Query.cs](../../SECS/Query.cs) последовательно проходит совпадающие архетипы, чанки и строки, передавая процессору изменяемые `ref`; типизированные chunk views уже предоставляют указатели и `Count`. Они позволяют добавить SIMD без обязательной переделки хранения. Выравнивание на ширину AVX не гарантировано; первый вариант должен использовать невыровненные загрузки.

[World.cs](../../SECS/World.cs) регистрирует `Action<World>` и выполняет системы последовательно. Создание, удаление и миграции сущностей выполняются сразу. [Archetype.cs](../../SECS/Archetype.cs) при удалении переставляет последнюю строку на место удалённой. Поэтому сохранённый курсор небезопасен при произвольных структурных изменениях.

[ComponentTypeRegistry.cs](../../SECS/ComponentTypeRegistry.cs) назначает локальные ID по порядку регистрации. Статический slot использует `Interlocked`, но это не делает registry или World потокобезопасными. [Entity.cs](../../SECS/Entity.cs) содержит ID и поколение, локальные для мира. `GetHashCode` и сырые байты структуры с padding нельзя использовать как переносимый checksum симуляции.

## Общий контракт детерминизма

При одинаковых начальном состоянии, входах с привязкой к тику, версии числового контракта и порядке систем каждый завершённый тик должен иметь одинаковые значения компонентов, Entity ID и поколения, а также одинаковую последовательность событий. Число работников, порядок завершения задач, SIMD ширина и границы кадров не входят в семантику симуляции.

Гарантия распространяется на системы нового API, соблюдающие контракт. Сам фреймворк не превращает произвольные float, MathF, физический движок, внешние вызовы или чтение часов в детерминированную игровую логику.

1. Системы идут в порядке `PreUpdate`, `Update`, `PostUpdate`, затем по фиксированному порядку регистрации. Первый scheduler параллелит задачи внутри системы; параллельное выполнение разных систем можно добавить после проверки зависимостей.
2. Перед системой фиксируются совпадающие сущности и их расположение. Канонический порядок нового API — `(Entity.Id, Entity.Version)`. Его нельзя менять из-за числа работников или SIMD ширины. Для legacy ForEach сохраняется прежний порядок обхода.
3. Логическая задача содержит до 64 последовательных элементов канонического списка. Последняя может быть короче. Это параметр алгоритма, а не функция `ProcessorCount`, ChunkCapacity или Vector.Count. Физические чанки служат местом хранения; один логический диапазон может пересекать несколько чанков.
4. Системы объявляют Read, Write и ReadWrite. Работник пишет только свои элементы. Чтение соседнего элемента компонента, который параллельно изменяется, требует отдельного read snapshot; в первом варианте такой режим отклоняется. Процессор имеет состояние на логическую задачу, а не на физический поток.
5. Типы компонентов и запросы подготавливаются до dispatch. Динамическая регистрация из работников запрещена. Runtime type ID не выступает внешним стабильным идентификатором схемы.
6. Структурные команды накапливаются отдельно и применяются после всей системы. Система после барьера видит их результат; внешние наблюдатели получают результат после завершения тика.
7. Команды и события имеют полный ключ `(tick, stage, systemOrder, sourceKind, sourceId, sourceGeneration, localOrdinal)` и сравниваются лексикографически по возрастанию всех полей. `sourceKind = 0` означает исходную сущность: sourceId/generation равны её ID/поколению. `sourceKind = 1` означает операцию без исходной сущности: sourceId равен logicalJobId, sourceGeneration равен нулю. localOrdinal — единый возрастающий счётчик всех команд и событий данного источника внутри системы. Поэтому entity-источники идут перед job-источниками и ключи не имеют неоднозначных совпадений. Завершение Task не назначает порядок.
8. Создание использует ticket, равный ключу команды Create, до барьера. Реальные ID назначаются при последовательном воспроизведении команд. В первом выпуске следующие команды того же источника с большим localOrdinal могут ссылаться на его ticket; обмен tickets между источниками до барьера запрещён. Это сохраняет Create перед обращением к его результату. Duplicate destroy, отсутствующий компонент и устаревшее поколение имеют явно описанные правила, совпадающие с последовательным эталоном.
9. Редукции используют фиксированный порядок листьев и операций. Первое исполнение может объединять вклады последовательно в каноническом порядке. Сумма partial sums допустима только при доказанной эквивалентности; checked/saturating fixed и float нельзя автоматически считать ассоциативными.
10. Общий изменяемый Random и случайность от worker ID запрещены. Если системе нужна случайность, она получает версионированный алгоритм со стабильным ключом `(seed, tick, system, entity, drawIndex)` или эквивалентным фиксированным потоком на сущность.

Версия конфигурации включает порядок систем, числовые правила и разбиение логических задач. Канонический список сохраняет состав задач при изменении ChunkCapacity. Стоимость сортировки и обновления этого списка измеряется отдельно; его можно кешировать до следующего структурного изменения.

## Fixed

Предлагаемый `SECS.Numerics.Fixed` — readonly unmanaged struct с одним `long Raw`, размером 8 байт и значением `Raw / 2^32`. Диапазон: от `-2147483648` до `2147483648 - 2^-32`; шаг около `2.3283064365e-10`. Допустимость 8 байт согласована; достаточность диапазона пока является проектным предположением.

Одно число занимает вдвое больше памяти, чем float. При равной ширине SIMD вектор содержит вдвое меньше таких чисел; умножение/деление также требуют широкого промежуточного результата. Поэтому ускорение относительно float является предметом замера, а не свойством выбранного формата.

- `+`, `-` и унарный минус имеют точный результат либо `OverflowException` независимо от checked-контекста вызывающего кода.
- `*` и `/` используют достаточное целочисленное промежуточное представление, например Int128. Результат округляется к ближайшему raw-значению, при равной дистанции — к чётному. Затем проверяется диапазон. Деление на ноль вызывает `DivideByZeroException`.
- FromRaw, целочисленные преобразования и FromRatio задают входные значения без float. FromRatio следует тому же округлению. Округление отрицательных результатов нельзя заменять арифметическим сдвигом без доказательства эквивалентности.
- Сравнение, равенство, Zero, One, MinValue и MaxValue работают с Raw. Сериализация имеет явно заданный порядок байтов. Переносимый checksum использует Raw и поля схемы.
- Преобразование в float/double явно используется на границе отображения. Неявное смешивание Fixed и float в симуляции исключается. NaN и Infinity отсутствуют.

Первый выпуск включает скалярную арифметику и точные тесты. Детерминированные sqrt, sin, cos, atan2, векторы и геометрия потребуют отдельных контрактов и измерения ошибки. Это условные расширения библиотеки; полная замена игровой математики не входит в первый промпт. SIMD для 64-битного fixed multiplication/division нельзя обещать по факту наличия SIMD: нужны широкие промежуточные значения и отдельный kernel.

## Time slicing

Предлагаемый opt-in `DeterministicRunner` имеет BeginTick, Advance с целым бюджетом логических задач и результат Pending или Completed. На BeginTick входы и параметры шага фиксируются; часы, delta от длительности кадра и повторный опрос ввода между срезами не влияют на этот тик. Например, 10 задач при бюджете 3 исполняются как 3, 3, 3, 1 на любом железе.

До Completed runner эксклюзивно владеет World. Внутренние записи могут происходить на месте; следующий этап начинается только после барьера предыдущей системы. Внешний код не читает изменяющийся мир и не использует заранее сохранённые refs, accessors или chunk pointers. Управляемые входы World проверяют владение, но C# unsafe-проверки не могут отозвать уже выданный указатель. Для отображения во время Pending потребитель держит последний завершённый снимок.

Это даёт логическую границу публикации без обязательного удвоения всего хранения. Если требуется одновременно читать живой World между срезами, понадобится staging/read snapshot как отдельное расширение, а его стоимость следует измерить.

Advance не пропускает работу и не увеличивает tick index из-за истечения бюджета. Бюджет ограничивает задачи, но не длительность произвольного callback, сортировки, подготовки и commit. Эти фазы нужно измерять отдельно; жёсткий предел миллисекунд не является гарантией плана.

Completed освобождает эксклюзивное владение и разрешает обычные обращения к World. Ошибка или Abort переводят runner в Faulted и сохраняют владение: частично изменённый мир остаётся закрытым для публичного доступа. Выдача Completed и обычный Reset в этом состоянии запрещены.

После завершения всех работников допускается полное восстановление из checkpoint последней завершённой границы, если такой механизм явно реализован. Только успешное восстановление освобождает владение. В первом выпуске без checkpoint используется DiscardWorld: runner дожидается работников, освобождает буферы, уничтожает рабочий World и затем закрывает владение; потребитель создаёт новый мир. Dispose активного или Faulted runner имеет те же явно документированные последствия, что DiscardWorld. Dispose после Completed освобождает только runner, сохраняя завершённый World. Публичный World.Dispose во время владения отклоняется; внутреннее уничтожение выполняет владелец после drain. Поддержка транзакционного rollback не подразумевается.

## Многопоточность

Параллельный executor использует тот же план, что и последовательный runner. При Advance(B) он получает те же B логических задач; меняется только назначение задач физическим работникам. Workers могут завершаться в любом порядке. Барьер, merge команд и публикация остаются каноническими.

Первый выпуск поддерживает независимые записи по сущностям и неизменяемые общие чтения. Доступ к World из callback, пересечение записей, неописанные побочные эффекты и чтение изменяемого соседа отклоняются либо исполняются отдельным явно последовательным шагом. `Action<World>` не получает скрытого Parallel.ForEach.

Race-free исполнение является необходимым условием. Проверки событий, Entity ID, редукций и команд доказывают именно детерминированный результат, а не только отсутствие исключений.

## SIMD

Первый выпуск добавляет типизированный путь ForEachChunk для 1–3 компонентов поверх существующих QueryChunkView и готовые числовые kernels. Встроенный пример — AddInt32 с явно заданным unchecked wraparound; Auto выбирает доступный Vector128/Vector API .NET 8, Scalar даёт принудительный эталон и fallback. Последний неполный блок обрабатывается скалярно.

Новые API снимают необходимость вручную организовывать обход чанков и выбор backend для поддержанных kernels. Они не являются компилятором произвольной игровой логики. Custom unmanaged struct не является допустимым Vector<T> только из-за unmanaged. Поля внутри компонента не раскладываются на новые колонки автоматически.

Векторный kernel может обрабатывать физически непрерывные участки логического диапазона. Ширина вектора не задаёт логические job ID, RNG, merge или порядок редукции. По мере расширения библиотеки Fixed kernels используют Raw и точно повторяют скалярное округление/overflow; неподдержанная операция имеет скалярный маршрут.

Детерминированный профиль сначала охватывает integer/Fixed. Float SIMD допускается отдельно с честно ограниченной гарантией; bitwise равенство с произвольной float-логикой не подразумевается. Измерять нужно весь путь запроса, dispatch, хвост и подготовку, а не только инструкции сложения.

Каждый промпт применяет этот общий контракт, содержит свою приёмку и требует обновить [сопутствующие изменения](RELATED_CHANGES.ru.md). При обнаружении несовместимости сначала записывается конкретный конфликт и обоснование; изменение потребителя не прячется в задачу ядра.

## Общая приёмка

- Существующие тесты SECS сохраняются. Новые сценарии проверяют завершённое состояние после каждого тика, ID/поколения, порядок событий, команды и числовые ошибки.
- Скалярный последовательный executor служит эталоном нового API. Legacy ForEach используется для сравнения только там, где порядок не меняет семантику задачи.
- Матрица исполнения включает работников 1, 2 и 4; бюджеты Advance 1, 3 и все задачи; chunk capacities 1, 63 и 256; Scalar и Auto; несколько seeds и повторные запуски. Число логических задач не меняется из-за этих параметров.
- Межплатформенная гарантия требует одних golden vectors и replay на .NET 8 x64 и ARM64; WASM проверяется, если заявляется его поддержка. Отключение intrinsics на x64 проверяет fallback, но не заменяет запуск на ARM64 или WASM.
- Checksum строится по явным полям и каноническим ID; дополнительно проверяется полный порядок событий. Сырые unmanaged buffers, padding и GetHashCode не являются форматом replay.
- Для Fixed сравниваются multiplication/division с независимым BigInteger-эталоном в тестах. Нужны отрицательные halfway случаи, MinValue/MaxValue, overflow и нулевой делитель.
- Бенчмарки публикуют runtime/CPU, режим исполнения, время подготовки/merge, память, аллокации и throughput. Измерение на одной машине не доказывает ускорение на любой машине. Скорость относительно float сообщается отдельно от правильности Fixed.
- Базовые проверки сборки и тестов выполняются локально с кешами внутри проекта. Полная сборка SECS.sln проверяет совместимость потребителей; она не доказывает детерминизм их игровой логики.
