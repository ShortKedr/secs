# Внутренний шаблон задачи: Time slicing в SECS

Статус: шаблон будущей реализации от 12 октября 2026 года. Перед применением сверить с текущими исходниками и [планом развития](../DEVELOPMENT_PLAN.ru.md). [Назначение и зависимости шаблонов](README.ru.md).

Реализуй opt-in выполнение одного логического тика за несколько кадров в SECS из SECS.sln. Прочти `docs/secs/DEVELOPMENT_PLAN.ru.md` и `docs/secs/RELATED_CHANGES.ru.md`. Это общий последовательный эталон будущей многопоточности. Допускаются только изменения SECS/, соответствующих SECS.Tests/, SECS.Benchmarks/ и docs/secs/; миграции потребителей записывай отдельно. Сохрани чужие изменения, legacy API и ограничения на файлы и удалённые состояния; Miro только для чтения.

1. Введи DeterministicRunner с BeginTick, Advance(int logicalJobBudget), Pending/Completed/Faulted и явным завершением владения. BeginTick фиксирует tick index, входы и шаг симуляции. Advance ограничивается логическими задачами, не миллисекундами. Новый тик, следующий зависимый шаг и публикация Completed невозможны до окончания требуемого барьера.
2. Введи явно зарегистрированные системы нового API с порядком стадий и Read/Write/ReadWrite декларациями. Процессор получает ограниченный диапазон данных и контекст, а не World. Существующие Action<World>, Run/RunAll и ForEach сохраняют синхронное поведение; произвольный callback не становится автоматически прерываемым.
3. Фиксируй список сущностей каждой системы в каноническом порядке ID/поколения. Создавай задачи по 64 элемента независимо от physical chunks, worker count и SIMD ширины. Храни descriptors, lifetime и состояние процессора на логическую задачу. Повторный Advance продолжает существующий план.
4. Запрети прямые структурные изменения во время активной системы. Введи буферы Create/Destroy/Add/Remove/Set и событий, полный лексикографический ключ с sourceKind/entity-or-job/localOrdinal из общего контракта, временные tickets и последовательное применение после всей системы. Ticket равен ключу Create; до барьера на него ссылается только тот же источник последующей командой. Опиши конфликтные команды и stale generation; следующая система должна видеть результат предыдущего барьера. Типы и запросы подготовь до dispatch.
5. Runner эксклюзивно владеет World до завершения тика. Рабочие записи могут быть in-place, но внешние обращения блокируются и ранее выданные refs/pointers не разрешены контрактом. Не обещай технически отозвать unsafe pointer. Отображение использует последний Completed снимок; staging/rollback всего мира не добавляй без отдельного обоснования.
6. Fault/abort не публикует частичный тик и сохраняет exclusive lease; публичный доступ, новый tick и обычный Reset отклоняются. Completed освобождает lease. Без готового полного checkpoint реализуй DiscardWorld: drain, cleanup, World.Dispose владельцем, затем закрытие lease; мир после этого нужно пересоздать. Dispose активного/Faulted runner следует этому правилу, Dispose после Completed сохраняет World. Внешний World.Dispose во время lease отклоняется. Восстановление из checkpoint может освобождать lease только после полного успешного восстановления границы тика, если такая функция добавлена явно.

Приёмка: сравни завершённое состояние, ID/поколения и полный порядок событий с эталонным запуском всех задач одним Advance. Используй бюджеты 1/3/all, capacities 1/63/256, пустые системы, три стадии, несколько запросов и создание/миграции между системами. Проверь повторное обновление, владение, запрещённые mutations, tickets, stale generation, fault/abort и освобождение ресурсов. Пример арифметики использует Fixed или явные целые, а не float.

Проверь, что неизменные входы с привязкой к tick дают один результат при разном числе кадров и что задача не пропускается и не выполняется повторно. Включи временные задержки только как инструмент проверки, а не источник решений симуляции. Проверь канонический trace отдельно от checksum.

Измерь подготовку плана, сортировку, выполнение, commit, память и allocations после прогрева. Advance с бюджетом не должен выдаваться за жёсткий лимит времени кадра. Сортировку/commit, способные вызвать паузу, отрази как конкретный результат измерения и направление следующей оптимизации.

Собери SECS, запусти тесты и проверь сборку SECS.sln локально с кешами внутри проекта. Итог: API, контракт владения, покрытые случаи, стоимость и список сопутствующих изменений. Это основа для промпта многопоточности, не второй независимый scheduler.
