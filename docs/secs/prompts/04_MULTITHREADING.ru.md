# Промпт реализации многопоточности в SECS

После реализации и проверки последовательного DeterministicRunner добавь в SECS его детерминированный parallel executor. Прочти `docs/secs/DEVELOPMENT_PLAN.ru.md`, `docs/secs/RELATED_CHANGES.ru.md` и фактический контракт runner. Используй существующий план задач, команды, правила публикации и эталон; не создавай отдельную модель тика.

Меняй SECS/, соответствующие SECS.Tests/, SECS.Benchmarks/ и docs/secs/. Сохрани legacy Action<World>/ForEach и чужие изменения. Не мигрируй SpaceBattle и остальных потребителей внутри этой задачи. Менять можно только текущий проект и локальные состояния; записи в Miro запрещены.

1. Физическое число работников является настройкой executor. Канонический список сущностей, логические задачи по 64 элемента и их ID остаются неизменными. При Advance(B) dispatch получает те же B задач, что и последовательный эталон. WorkerCount/ProcessorCount и завершение Task не задают семантический порядок.
2. Состояние processor, event и command buffers привяжи к logicalJobId. Не разделяй mutable struct processor между потоками. Разреши независимые записи в свои элементы и только неизменяемые общие чтения. Учитывай aliasing одного компонента в разных параметрах запроса.
3. Проверь декларации доступа до запуска. Пересекающиеся writes, чтение параллельно изменяемого соседа, dynamic component registration и внешний World в callback должны быть отклонены либо обработаны явно последовательным шагом. Безопасность не выводится из одного where T : unmanaged.
4. По окончании системы дождись всех её задач, затем воспроизведи команды и события по полному лексикографическому ключу с sourceKind из последовательного runner. Создание получает ID только при replay; ticket равен ключу Create, а до барьера на него ссылаются только последующие команды того же источника. Результат сохраняется при любой скорости работников.
5. Редукции повторяют фиксированную последовательность операций или доказанно эквивалентное дерево с фиксированными листьями. Не объединяй по порядку завершения или физическим worker partial sums. Checked Fixed и float не считаются ассоциативными по умолчанию.
6. Не используй общий Random или seed от worker ID. Для случайного примера зафиксируй алгоритм/версию и ключ seed/tick/system/entity/drawIndex либо эквивалентный поток на сущность. Не используй System.HashCode как переносимый RNG/checksum.
7. Ошибки собираются после безопасного завершения активных задач; публичная ошибка выбирается по каноническому ключу, не по первому завершившемуся Task. Faulted тик не публикуется и сохраняет exclusive lease. Следуй lifecycle последовательного runner: полное восстановление освобождает lease только при явно поддержанном checkpoint, иначе DiscardWorld/Dispose делает drain, cleanup и уничтожение рабочего World. Память не освобождается до завершения работников; после Completed Dispose сохраняет завершённый World.

Приёмка: повторные replay с workers 1/2/4, budgets 1/3/all и capacities 1/63/256. Сравни значения по Entity ID/поколению и полный trace событий после каждого Completed тика, включая создание/удаление, tickets, миграции, редукции, RNG и конфликты. Внеси контролируемые задержки, меняющие порядок завершения, и проверь одинаковый результат и канонический fault. Не называй совпадение одного checksum полным доказательством.

Добавь сценарии на независимых записях, general read-only inputs и отказе для cross-row read/write. Проверь lifetime refs/pointers, владение runner и корректность cleanup. Скаларный последовательный runner является эталоном; сохранение legacy callback порядка проверяется отдельно.

Измерь throughput и overhead для малой и большой нагрузки, планирования, dispatch, merge, команд, памяти и allocations после прогрева. Отчёт с ускорением включает конкретный CPU/runtime и параметры; больше работников не обязано ускорять малую нагрузку.

Собери SECS, запусти релевантные и регрессионные тесты, проверь совместимость SECS.sln локально с кешами внутри проекта. Зафиксируй supported access patterns, ошибки, measured speedup и непроверенные платформы. Обнови сопутствующие изменения с причиной каждого пути вне SECS/.
