# Сопутствующие изменения при развитии SECS

Основной код новых возможностей относится к `SECS/SECS.csproj`. Этот список фиксирует изменения вне ядра и причину каждого. Наличие SpaceBattle в `SECS.sln` не включает развитие игры в основные задачи фреймворка.

Статус: границы будущих задач, а не журнал уже внесённых изменений. После реализации конкретной задачи перечисляйте фактически изменённые пути и проверки в её отчёте.

[План развития](DEVELOPMENT_PLAN.ru.md) · [Карта документации](../README.ru.md)

## Необходимые изменения для приёмки ядра

| Проект или путь | Что потребуется | Почему это нужно | Когда |
| --- | --- | --- | --- |
| `SECS.Tests/` | Числовые golden vectors, BigInteger-эталон; сценарии continuation, владения World, structural commands, ID, событий, конфликтов и parallel replay | Существующие последовательные тесты не проверяют новые гарантии | В каждом промпте вместе с изменением ядра |
| `SECS.Benchmarks/` | Отдельные Fixed/float/int, Scalar/SIMD и sequential/parallel/sliced сценарии; измерение setup/dispatch/merge и памяти | Заявления «быстрый», «SIMD» и «многопоточность» требуют измерений; новые пути имеют накладные расходы | После корректности соответствующего пути |
| `docs/secs/` | Контракты арифметики, ownership, продолжения тика, доступа и supported kernels; команды воспроизведения | Пользователь должен понимать, какой код подходит новому API и что гарантируется | По мере реализации |

У тестов и бенчмарков уже есть ProjectReference на SECS. Новый числовой модуль предлагается внутри SECS, поэтому добавление проектов или изменение `SECS.sln` для первого выпуска не требуется.

## Изменения при подключении потребителей

Эти изменения условные. При сохранении legacy API они не нужны для сборки или прежнего поведения потребителей и не выполняются в основных промптах.

| Проект или область | Условие и изменение | Почему именно это нужно |
| --- | --- | --- |
| `SECS.Sample/` | При демонстрации новых возможностей добавить отдельный Fixed + runner + chunk kernel пример, сохранив legacy пример | Текущий пример показывает float и синхронный Action/ForEach; он не объясняет правила новых возможностей |
| `SECS.OtherBenchmarks/`, `Benchmarks.Local/Comparison.csproj` | Если новые пути включаются в сравнение ECS, завести отдельную одинаковую нагрузку и оставить старый baseline | Замена числового формата или модели выполнения только у SECS делает сравнение разных алгоритмов вместо сравнения ECS |
| Адаптер `SpaceBattle.SECS/` | Только при подключении runner/SIMD мигрировать подходящие системы и описать Read/Write, команды и границы тика | Адаптер должен передавать доступы и владение явно; legacy ForEach сам по себе не содержит этой информации |
| Симуляция `SpaceBattle.Core/` | Только при запросе детерминизма игры проверить диапазоны, перевести влияющие на результат числа на Fixed, заменить или ограничить недетерминированные внешние вычисления и RNG | Детерминированный storage/executor не задаёт числовую семантику сторонней физики и пользовательского кода |
| Хосты `SpaceBattle.Game/`, `SpaceBattle.Headless/` и веб-проекты | Только при подключении time slicing привязать ввод к логическому тику, вызывать Advance и отображать последний Completed снимок; настроить доступный executor | Кадры, отображение и количество работников принадлежат хосту; чтение изменяющегося World во время Pending нарушает контракт |
| Отчёты в `docs/space-battle/` и root README | Только после фактического подключения и измерения обновить утверждения, инструкции и результаты | Старые замеры и checksum не доказывают свойства новой реализации |

Веб-проекты перечислены как возможные потребители, а не как расширение текущей задачи за пределы SECS.sln. Миграция сторонней физики не заявляется обязательным изменением ядра и требует отдельного решения, если потребуется детерминизм игры.

## Проверки платформ и сборки

Cross-platform приёмка требует локальных запусков либо подготовленного способа воспроизведения golden vectors на каждой заявленной платформе. Добавление файла CI workflow локально может быть отдельным сопутствующим изменением, но запуск удалённых jobs, push или изменение удалённых настроек запрещены текущими инструкциями.

Если среда для ARM64/WASM отсутствует, результат отмечается как непроверенный на этой платформе. Принудительный Scalar на x64 не выдаётся за проверку другого CPU.

После каждого шага собираются SECS и зависимые проекты SECS.sln для проверки совместимости. Возникшая ошибка записывается с конкретным проектом, вызвавшей её сигнатурой и минимальным исправлением. Изменение потребителя выполняется только в явно указанном сопутствующем объёме.

## Правила внесения изменений

Перед реализацией каждого промпта уточнить этот список по фактическому diff. Для нового пути указать обязательность, затронутый публичный контракт и причину. Не добавлять массовую замену float, переписывание SpaceBattle, обновление чужих benchmarks или vendor-кода под видом автоматической миграции.

Новые примеры, миграция игры, дополнительная математика и поддержка новых runtimes не являются условиями первого выпуска ядра, если соответствующая возможность не объявлена частью его гарантий.
